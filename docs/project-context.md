# Dondok 프로젝트 컨텍스트

이 문서는 PM, DB, 프론트엔드, 백엔드 역할이 같은 제품 전제와 결정을 공유하기 위한 기준 문서다. 기능이나 정책을 바꿀 때 관련 상세 문서와 함께 이 파일을 갱신한다.

## 제품 목표

N명의 구성원이 각자 소유한 자산을 하나의 가계부에서 공유해 사용하고, 실제 거래 주체와 작성자를 구분해 기록하는 자체 호스팅 웹 서비스다.

## 역할

- Project Manager: 전체 사용자 흐름, 범위, 결정사항과 역할 간 경계 유지
- Database: PostgreSQL 스키마, 제약, 인덱스, 원장, 쿼리 성능과 동시성
- Frontend: 모바일 우선 UX, 접근성, 서버 상태와 충돌·재조회 처리
- Backend: 명확한 API, 도메인 추상화, 트랜잭션, 권한과 동시성
- Quality Control: 독립 인수 조건, Playwright E2E, 실패 증거와 책임 분류, 회귀 테스트
- UX/UI Designer: 브랜드, 모바일 우선 사용자 흐름, 디자인 시스템, 접근성, 프론트엔드 구현 검수

## 기술 방향

- Database: PostgreSQL, Flyway
- Backend: Java, Spring Boot stable patch, Spring Data JPA
- Architecture: feature-first modular monolith
- Frontend: React SPA, Vite, TypeScript, React Router, `vite-plugin-pwa`
- Server state: TanStack Query
- UI: shadcn/ui + Tailwind CSS
- Synchronization: REST command + entity version 충돌 방지 + 화면 진입·focus·수동 재조회
- Deployment: 개인 Mac mini, 구매한 도메인과 Cloudflare DNS, 기존 Nginx Proxy Manager HTTPS, Docker Compose
- Repository layout: `backend/`와 `frontend/` 독립 관리, `e2e/`와 `infra/` 분리
- Repository: GitHub, branch/PR 기반 관리 예정
- Redis: 다중 애플리케이션 서버가 필요해질 때만 검토

## 핵심 사용자 흐름

1. 로그인 아이디, 이름, 이메일, 비밀번호로 누구나 가입한다.
2. 로그인 아이디는 외부에 노출하지 않으며 공개 핸들과 사용자 검색도 제공하지 않는다.
3. 가계부가 없는 사용자는 새로 만들거나 초대 URL·코드로 기존 가계부에 참여한다.
4. 한 가계부에는 동등한 권한의 활성 멤버 N명이 존재한다.
5. 자산마다 소유자인 구성원 한 명을 지정한다.
6. 모든 활성 멤버는 모든 자산을 조회하고 거래에서 사용할 수 있다.
7. 수입·지출·이체의 거래 주체는 현재 멤버가 기본이며 다른 멤버를 선택할 수 있다.
8. 작성자는 서버가 인증 세션에서 자동 기록한다.
9. 카드 구매는 구매일 지출 통계와 카드 결제 예정액에 즉시 반영한다.
10. 카드 상세에서 미결제 내역이나 부분 금액을 선택해 결제를 기록하면 선택 계좌→카드 이체가 자산에 반영되며 소비 통계에는 다시 잡히지 않는다. 자동 결제는 실행하지 않는다(D-069).

## 확정한 설계 결정

### D-001 데이터 소유 경계

`ledger_book + ledger_member`가 이름 없는 공동 데이터 소유 경계다. 한 사용자는 동시에 하나의 가계부에만 참여할 수 있고 한 가계부는 N명의 멤버를 가진다.

### D-002 공개 식별자와 초대

로그인 아이디는 인증 전용이다. 공개 핸들·사용자 검색 없이 초대 URL과 직접 입력 코드를 제공한다. 직접 입력 코드는 숫자 6자리, URL은 별도 고강도 token이며 DB에는 두 원문이 아닌 각각의 SHA-256 digest만 저장한다. 로그인한 사용자가 가계부를 확인하고 수락하면 즉시 참여하고, 초대는 7일 만료·1회 사용이다.

### D-003 자산 소유와 공유

자산은 같은 가계부의 구성원 한 명을 소유자로 둔다. 공동 소유는 제공하지 않는다(D-061). 소유 표시는 통계 메타데이터일 뿐 접근 권한이 아니다. 모든 활성 멤버가 모든 자산과 설정을 동일하게 등록·수정·삭제하고 거래에서 사용할 수 있다.

### D-004 잔액과 거래

자산에서 사용자가 입력하는 금액과 날짜는 각각 `기준일 잔액`과 `잔액 기준일`이다. 기준일 잔액은 선택한 날짜 시작 시점에 실제로 보유한 금액을 뜻한다. 기준일 이전 거래도 허용하고 수입·지출 통계와 원장 이력에는 그대로 포함하지만, 그 거래의 posting은 기준일 잔액에 이미 반영된 것으로 보아 기준일 이후 잔액에 다시 더하지 않는다. 기준일 당일 거래부터 기준일 잔액에 합산하며 현재 잔액은 `기준일 잔액 + 기준일 당일 이후 유효 posting`으로 계산한다. 원화만 지원하고 금액은 `bigint` 원 단위다.

V18 이전 자산은 배포 시 보이던 현재 잔액이 바뀌지 않도록 기존 `OPENING_BALANCE` posting과 기준일 이전 유효 posting의 합을 새 기준일 잔액으로 이관한다. 공개 API의 `openedOn`·`openingBalanceWon` 필드명은 기존 PWA 호환을 위해 유지하되 사용자 문구와 계산 의미는 각각 잔액 기준일·기준일 잔액이다. 신용카드의 기준일 이전 구매 charge는 통계·원장·구매 관리 이력에는 남지만 `absorbed_by_balance_anchor`로 표시해 명세와 결제 예정액에는 다시 합산하지 않는다.

### D-005 거래 주체와 작성자

`performed_by_member_id`는 실제 경제활동 주체, `created_by_member_id`는 앱 입력자, `updated_by_member_id`는 최종 수정자다. 수입·지출·일반 이체의 거래 주체는 구성원 한 명이며 로그인한 본인을 기본으로 다른 구성원을 선택할 수 있다. 공동·분할 주체는 두지 않고 소비 통계는 거래 주체 기준이다. 사용자 화면에는 `거래 주체`나 `거래한 구성원` 같은 내부 용어를 노출하지 않고 유형별로 `누가 받았나요?`·`누가 썼나요?`·`누가 옮겼나요?`를 사용하며, 상세에서는 `받은 사람`·`쓴 사람`·`옮긴 사람`으로 표시한다. 자동 카드 정산과 카드 선결제는 생성 시점의 카드 소유자를 거래 주체로 기록하고 상세에서는 `카드 명의자`로 표시한다. 결제 계좌는 자금 출처이며 수입·지출 통계에서 제외한다(D-062).

### D-006 공동 카테고리 삭제

수입·지출 방향마다 `OTHER` fallback을 하나 둔다. 일반 카테고리 삭제 시 연결된 거래를 같은 방향 fallback으로 한 트랜잭션에서 이동하고 카테고리를 archive한다.

### D-007 자산 삭제·사용 종료

자산 삭제·사용 종료는 서버 미리보기 뒤 같은 `previewToken`과 자산 `expectedVersion`으로 실행한다. 기준일 잔액을 위해 만든 내부 `OPENING_BALANCE` 기록은 실제 거래 이력에서 제외한다. 실제 거래 이력과 다른 보존 참조가 없으면 내부 기준 잔액 기록을 함께 제거하고 물리 삭제하며, 하나라도 있으면 내부적으로 `archived_at`을 기록하되 사용자에게는 `사용 종료`로 표현한다. preview 이후 이력·잔액·연결·version이 달라지면 `412`로 전체를 거부하며 사용자가 최신 미리보기를 다시 확인해야 한다.

활성 신용카드·체크카드·적금의 출금 계좌이거나 미처리 카드 결제 schedule의 자금 출처인 경우에만 먼저 연결을 변경하도록 차단한다. 이미 사용 종료된 자산의 비활성 설정이 참조 중이면 자동으로 연결을 지우거나 해결 불가능한 차단을 만들지 않고 대상도 물리 삭제 대신 사용 종료 상태로 남겨 참조를 유지한다. 현재 잔액과 대상 카드의 미결제 명세는 결과 경고이며 삭제·사용 종료를 막지 않는다. 사용 종료 자산은 활성 50개, 활성 그룹과 신규 거래·연결 계좌 선택기에서 제외하지만 잔액은 순자산에 계속 포함하고 과거 거래·통계를 유지한다. 사용 종료한 카드는 새 결제를 거부하며, 다시 사용하면 직접 결제를 기록할 수 있다. 자동 정산 schedule은 재생성하지 않는다(D-069).

### D-008 카드 소비와 정산

카드 구매는 `EXPENSE`로 구매일 통계에 즉시 반영하고 카드 자산 부채를 늘린다. 결제일에는 `TRANSFER/CARD_SETTLEMENT`로 결제 계좌 잔액을 줄이고 카드 부채를 줄인다. settlement는 수입·지출 통계에서 제외한다.

일시불·할부 구매를 지원하되 카드사 이자는 계산하지 않고 사용자가 별도 거래로 입력한다. 정규 결제일 전 카드대금은 전액 또는 지정한 일부 금액으로 여러 번 선결제할 수 있다. 각 결제는 자산만 이동하는 통계 제외 이체이며 명세 잔액을 초과할 수 없다. 카드의 음수 기준일 잔액도 잔액 기준일과 카드 마감·결제 설정에 따른 명세에 넣으며, 이미 지난 결제일이면 catch-up 정산 대상이 된다. 기준일 이전 카드 구매는 그 기준일 잔액에 이미 포함된 이력으로 보아 명세에 중복 청구하지 않는다. 이후 실제 환불은 미결제 기준일 명세를 먼저 줄이고, 이미 결제한 부분은 최신 실제 결제부터 해당 결제 계좌로 반환한다.

카드 정산의 자금 출처는 설정된 결제 계좌다. 장부상 결제 계좌 잔액이 부족해도 남은 금액 전액을 기록하고 계좌의 음수 잔액을 허용하며, 잔액 부족을 실패나 재시도 상태로 만들지 않는다.

### D-009 날짜와 통계

경제활동일은 `DATE`다. 이체와 카드대금 정산은 수입·소비 지출 통계에서 제외하며, 일반 이체의 적금·투자 목적은 D-068의 별도 납입·회수 통계에 반영한다. 생성·수정 시각만 `TIMESTAMPTZ`를 사용한다. 카드 결제 예정일은 `Asia/Seoul` 기준 한국 영업일 달력과 공식 공휴일 데이터를 사용하며, 말일 보정 후 비영업일이면 다음 한국 영업일로 순연한다.

### D-010 유지보수 추상화

깊은 JPA 상속 계층을 만들지 않는다. 공통 영속 데이터는 단일 entity, 특수 데이터는 1:1 composition, 동작 차이는 sealed command와 Strategy/Policy, 생성은 Factory로 분리한다. 기술 공통 필드의 얕은 `@MappedSuperclass`만 허용한다.

### D-011 동시성과 충돌 처리

일반 수정은 편집 시작 때 읽은 entity version을 저장 요청에 포함하고, 현재 version과 다르면 변경을 전혀 적용하지 않은 채 `412 VERSION_CONFLICT`를 반환한다. 필드 자동 병합은 하지 않고 draft를 보존해 사용자가 최신값에 다시 적용한다. 중복 생성은 idempotency/unique, 초대·카테고리 삭제·카드 명세 정산·자산 50개 제한의 경쟁은 필요한 aggregate만 행 잠금한다.

MVP에는 SSE와 sync outbox를 두지 않는다. 작성 세션은 command 응답으로 자기 TanStack Query 캐시를 갱신·무효화하고, 다른 세션은 화면 진입·window focus·사용자 새로고침 때 최신 데이터를 조회한다.

### D-012 동등 권한과 알림 범위

모든 활성 멤버는 동일 권한이다. 역할, 소유자 전용 권한, 승인 흐름과 등록·수정 사용자 알림을 두지 않는다.

### D-013 삭제와 보정

`기록 정정`과 `환불 처리`를 분리한다. 기록 정정은 잘못 입력한 과거 원거래·charge·명세·정산을 원 결제일 기준으로 소급 교정한다. 환불은 원 구매·결제 이력을 보존하고 환불일 통계를 상쇄하며, 미결제분은 카드 부채를 줄이고 결제 완료분은 최신 결제부터 실제 원 결제 계좌로 반환한다. 모든 posting·charge·명세 변경은 한 트랜잭션으로 처리해 잔액 불일치를 허용하지 않는다. 개인 나가기는 제공하지 않고 구성원은 초대로 추가만 가능하다. 가계부 전체 연결 해제는 `ledger_book` hard delete와 하위 데이터 cascade delete로 처리한다.

카드 구매 생성 시 당시 카드의 마감일·결제일·결제 월 offset·할부 수를 billing snapshot으로 고정한다. 환불은 원 구매와 연결된 `CARD_REFUND` 거래로 남겨 일별 원장에 `환불 +금액`으로 보이고, 환불일의 지출 집계에서 차감한다. 정정·환불은 서버 preview 후에만 apply하며 preview token은 구매 version과 영향받는 명세·결제·기존 환불 상태를 포함한다. apply에서 다시 행 잠금·version·token을 확인하고 stale이면 `412`로 전체를 거부한다.

기록 정정 UX는 폼의 `정정 저장`을 누르면 서버 preview 결과를 확인 dialog에 보여주고, dialog 안의 `저장`으로 apply하거나 `취소`로 입력을 보존한 채 닫는 단일 확인 흐름이다. 서버 preview를 별도의 인라인 `변경 내용 확인` 단계로 노출하지 않는다. 환불의 별도 확인 흐름은 유지한다.

### D-014 기본 통계

통계 첫 화면은 로그인한 현재 구성원의 경제활동이 기본이다. `나 · 각 구성원 이름 · 모두` compact 선택으로 전환하며, 선택 월 수입·지출·순액, 카테고리 비중과 선택 월이 속한 연도의 1~12월 수입·지출 합계에 모두 같은 거래 주체 기준을 적용한다. 자산 소유자와 카테고리는 별도의 선택형 세부 필터로 함께 적용한다. 일별 추이는 통계에서 제공하지 않고 홈의 일별 원장에서 확인한다.

### D-015 QC와 오류 인계

QC는 프론트·백엔드와 독립적으로 테스트를 작성하고 실행한다. Playwright 실패는 trace·screenshot·network·console·seed manifest·request ID·백엔드 로그를 묶어 FRONTEND/BACKEND/CONTRACT/TEST/INFRA로 분류한다. HTTP request ID를 응답·백엔드·DB/audit까지 추적한다. 실행 가능한 기능 전에는 실패 placeholder를 만들지 않는다.

PR은 build·unit·PostgreSQL integration·OpenAPI drift·핵심 Chromium E2E를 필수 gate로 둔다. 릴리스는 전체 핵심 E2E·이전 migration·같은 row 동시성·백업 복원을 추가하고, 실패 seed는 24시간, 마스킹한 artifact는 14일 보관한다. Chromium·Edge·macOS/iOS Safari를 공식 지원하고 Firefox는 smoke 범위로 둔다.

### D-017 저장소·환경변수·Mac mini 배포

한 public GitHub 저장소 안에서 `backend/`, `frontend/`, `e2e/`, `infra/` 경계를 분리한다. 실제 환경파일과 secret은 전 계층에서 Git과 Docker build context에서 제외하고 안전한 `.env.example`만 추적하며 secret scanning·push protection·CI Gitleaks를 사용한다. 프론트엔드·Playwright의 개발, CI와 Docker build는 루트 `.nvmrc`, npm engine, Actions와 Dockerfile에 고정한 Node.js `24.18.0`을 단일 기준으로 사용한다. 공개 저장소의 PR 코드가 Mac mini에서 실행되지 않도록 repository-level self-hosted runner를 public 애플리케이션 저장소에 연결하지 않는다. 배포 runner와 workflow는 소유자만 접근하는 별도 private 배포 저장소에 두고, public `main`의 현재 SHA와 그 SHA의 성공한 CI를 대조한 뒤에만 같은 revision을 checkout해 실행한다. 백엔드와 프론트엔드는 각각 multi-stage·non-root Dockerfile을 가지며 Mac mini에서는 공개 도메인과 HTTPS를 제공하는 reverse proxy만 WAN에 공개하고 backend와 PostgreSQL은 내부 network에서 운영한다. PostgreSQL의 운영자용 LAN 접근은 D-044의 사설 주소 bind만 예외로 허용한다. 애플리케이션 이미지는 Git SHA와 digest로 식별하고 배포 전 백업·격리 복원 drill, Compose health, 실패 시 직전 SHA 이미지 rollback을 수행한다. healthcheck, 재시작 정책, PostgreSQL 영속 volume, 매일 1회 30일 백업·주 1회 암호화 off-device 복제와 복원 검증을 배포 완료 조건으로 둔다. 운영 PostgreSQL의 삭제는 즉시 반영하고 암호화 백업의 삭제 전 데이터는 rotation 전까지 최대 30일 보존한 뒤 자동 만료한다.

운영 origin은 비공개 운영 설정의 `DONDOK_PUBLIC_URL`로 관리한다. 2026-10-09 사용자 결정으로 가비아에서 구매한 도메인과 Cloudflare DNS로 DuckDNS를 대체한다. 실제 운영 도메인은 비공개 설정에만 둔다. A record는 Mac mini의 현재 공인 IPv4를 가리키고, 사용자 LaunchAgent가 5분마다 확인해 변경된 경우에만 Cloudflare API로 갱신한다. DNS only·TTL 등 기존 레코드 속성은 보존하고 `www`는 기본 도메인의 CNAME을 사용한다. Cloudflare API token은 해당 zone의 DNS Edit 권한으로 제한하고 저장소·대화·process argument·로그에 넣지 않으며 Mac mini의 사용자 전용 0600 JSON 파일에 보관한다. 설치 시 실제 수정 권한을 확인하며, 기존 DuckDNS 작업 중단은 새 자동 실행 성공과 외부 접속 확인 후 별도로 진행한다. 기존 Nginx Proxy Manager가 HTTP-01로 Let's Encrypt 인증서를 발급·갱신하고 `host.docker.internal`의 `DONDOK_FRONTEND_PORT` 포트로 전달하며 실제 포트는 비공개 운영 설정에서 관리한다.

### D-020 세분화 반응형 프론트엔드

모바일, iPad·태블릿 세로와 가로, 데스크톱을 모두 일급 지원한다. 단순 확대가 아니라 사용 가능한 콘텐츠 폭에 따라 내비게이션·목록·달력·폼·통계를 재배치하며 화면 크기가 달라도 정보 구조, 기능, 데이터 의미를 유지한다. 모든 프론트엔드 기능은 대표 viewport와 breakpoint 경계에서 접근성, 전체 페이지 가로 overflow, safe area, 긴 데이터, 회전·resize 중 draft·필터·focus·서버 상태 보존을 검증해야 완료된다. 정확한 CSS breakpoint는 UX/UI와 Frontend가 공통 규칙으로 관리하는 되돌릴 수 있는 구현 세부다.

`320–767px` 모바일은 휴대폰 앱 크롬을 사용한다. push형 상세·수정 화면의 뒤로가기와 제목은 safe area를 반영한 sticky 상단 바 한 줄에 통합하고, `홈 · 기록 · 자산 · 통계 · 설정`은 화면 모서리와 거리를 둔 둥근 floating 5탭 dock으로 표현한다. 하단 dock의 최상위 `기록` 탭인 새 거래 화면에는 뒤로가기나 별도 sticky 상단 바를 두지 않고 다른 최상위 데이터 화면처럼 본문 제목부터 시작한다. 일반 홈·자산·통계·설정 화면에도 브랜드나 utility를 위한 상단 바를 두지 않고 콘텐츠가 safe area 다음에서 바로 시작한다. 설정 첫 화면에는 별도 가계부 복귀 행을 두지 않고 로그아웃을 설정 안에 둔다. `768px` 이상 iPad·태블릿은 80px icon rail, `1280px` 이상 데스크톱은 높이 64px의 고정 상단 메뉴를 사용한다. 로고와 홈·기록·자산·통계를 한 줄로 두고 설정은 오른쪽에 분리한다. 기본 medium·선택 semibold와 초록 밑줄로 상태를 구분한다. 본문 왼쪽 여백을 없애고 82rem 최대 폭을 유지하며 sticky 날짜·요약은 상단 메뉴 높이 아래에 둔다. `1024px` 이상의 거래 입력은 작성 폼과 같은 draft를 즉시 읽는 고정 요약 rail을 나란히 두되 작성 control과 저장 행동을 중복하지 않는다.

### D-021 React PWA

프론트엔드는 React SPA + Vite + TypeScript + React Router로 확정하고 `vite-plugin-pwa`를 사용한다. PWA는 홈 화면 설치, standalone 실행, manifest·아이콘과 버전된 정적 앱 셸 캐시만 제공한다. API 응답·금융 데이터 캐시와 오프라인 mutation queue는 만들지 않는다. 오프라인 쓰기를 차단하고 draft를 보존하며, 새 버전은 작성 중 입력을 지우지 않도록 사용자 확인 후 갱신한다.

### D-022 공개 가입과 계정 복구

누구나 가입할 수 있다. 이메일 인증 후 서비스를 사용하며 이메일 기반 비밀번호 찾기·재설정과 로그인 상태 비밀번호 변경을 제공한다. 로그인 성공 시 JDBC 서버 세션 ID만 담은 `Secure`·`HttpOnly`·`SameSite=Lax` 쿠키를 최대 90일 영속화해 브라우저나 설치형 PWA를 닫았다 열어도 자동 로그인한다. 비밀번호·인증 token은 브라우저 저장소에 두지 않는다. 서버 세션은 미사용 30일·생성 후 절대 90일에 만료하고, 다중 기기와 현재/전체 기기 로그아웃을 제공한다. 명시적 로그아웃은 현재 쿠키와 세션을 즉시 폐기하며 30분·1회용 reset token으로 비밀번호를 바꾸면 기존 모든 세션을 만료한다.

### D-023 테마와 목록 성능 경계

테마는 첫 방문에 OS 설정을 따르고 사용자가 설정 화면에서 `system/light/dark`를 선택하면 해당 기기에만 기억한다. 로그인·온보딩·앱 상단과 sidebar에는 theme control을 반복하지 않고 설정의 단일 선택기에서만 바꾼다. breakpoint 전환 후에도 선택 상태와 실제 theme가 어긋나지 않아야 한다. dark 표면은 완전한 semantic color token과 `color-scheme: dark`를 사용하고 선택·hover·focus·placeholder·icon의 대비를 함께 검증한다. 가계부당 활성 자산은 최대 50개다. 거래 수에는 제품 상한을 두지 않고 cursor pagination·TanStack infinite query와 필요한 범위의 목록·달력·통계 query로 읽으며 전체 원장을 무제한 로드하지 않는다.

### D-024 이름 없는 단일 가계부

가계부는 사용자가 이름을 붙여 관리하는 별도 목록 항목이 아니라 계정이 속한 단 하나의 공동 기록 공간이다. 생성할 때 이름을 입력받지 않고 `ledger_book`에도 사용자 지정 이름을 저장하지 않는다. 현재 가계부와 초대 미리보기는 이름 대신 구성원과 참여 상태로 식별하며, 가계부 전환·이름 변경 기능은 만들지 않는다. `ledger_member.user_id` 전역 unique와 application 충돌 처리로 한 사용자의 생성·초대 수락 경쟁에서도 하나의 가계부 참여만 허용한다.

### D-025 초대 완료와 설정 경계

초대 URL·코드 확인 화면은 가계부가 없는 사용자의 참여 전 흐름에서만 존재한다. 수락 성공 즉시 초대 route를 종료하고 홈으로 이동하며, 이미 가계부에 참여한 사용자가 초대 route를 열면 초대 API를 호출하지 않고 홈으로 돌려보낸다. 참여 후 구성원 확인, 새 초대 발급·취소와 발급 내역 관리는 가계부 설정에서만 제공하고 홈에서는 초대 행동을 노출하지 않는다.

### D-026 가계부 중심 홈과 절제된 데이터 UI

참여 후 홈은 구성원 안내나 장식성 요약 화면이 아니라 실제 공동 가계부다. 기본은 월간 달력이며 각 날짜에 수입을 녹색 `+금액`, 지출을 빨간색 `-금액`으로 함께 표시한다. 좁은 셀의 금액은 `만·천만·억·조` 단위의 짧은 표기로 말줄임표 없이 읽히게 한다. 날짜를 선택하면 정확한 원 단위 수입·지출 합계와 거래 내용을 모바일에서는 전체 화면 일별 상세로, `768px` 이상에서는 달력 위 중앙 dialog로 같은 DOM에서 확인한다. 상세 화면은 URL의 월·선택일·열림 상태를 source of truth로 삼아 새로고침·직접 진입·브라우저 뒤로 가기를 지원하고, 이전 날·다음 날 행동은 월·연도 경계를 넘어 이동한다. 같은 화면에서 `월별/일별` 보기를 바꾸고, 일별 보기는 날짜별 거래 행을 bounded cursor pagination으로 연속 스크롤한다. 월·보기·선택일·상세 상태는 화면 크기 변경에도 유지한다.

휴대폰 홈은 별도 `가계부` 제목과 기록·새로고침 header를 표시하지 않고 safe area 다음의 월 탐색부터 시작한다. 화면 맨 위에서 아래로 당겨 새로고침하면 브라우저 전체 reload가 아니라 현재 활성 거래 query를 무효화해 다시 조회한다. `768px` 이상에서는 가계부 제목과 명시적 새로고침을 유지한다. 화면 크기와 관계없이 새 기록은 선택한 날짜 상세의 기록 행동으로 열고 해당 날짜를 초깃값으로 사용한다.

홈의 데스크톱 배치는 월간 달력·일별 원장을 넓은 주 작업 영역에 두고 이번 달의 수입·지출·순액을 오른쪽 요약 rail에 둘 수 있는 dashboard다. 휴대폰·iPad 세로에서는 같은 요약 DOM을 달력 위의 한 행으로 복귀하고, 요약 수치를 장식성 KPI 카드로 반복하지 않는다.

구성원 확인과 초대는 설정에만 두며 홈과 중복되는 별도 `내역` 핵심 메뉴는 만들지 않는다. 모바일 최종 메뉴는 `홈 · 기록 · 자산 · 통계 · 설정`이고, iPad는 네 데이터 메뉴와 하단 설정 링크, 데스크톱은 네 상단 메뉴와 오른쪽 설정 링크로 위계를 나눈다. 로그아웃은 설정 안에 두며 일반 앱 상단과 sidebar에는 반복하지 않는다. 가계부가 아직 없는 가입·초대 전 화면은 설정에 접근할 수 없으므로 기존 상단 로그아웃을 유지한다. 데이터 화면은 표·행·구분선·금액 정렬을 우선하며, 구조적 카드 컨테이너를 사용하지 않는 상세 원칙은 D-027을 따른다. 입력과 작은 컨트롤의 radius는 4~6px, 모달·시트·popover는 최대 8px를 사용한다. 휴대폰 하단 내비게이션은 기기 모서리와 조화되는 하나의 floating 표면이므로 20~24px 외곽 radius와 최소 elevation을 허용하되 각 tab을 개별 카드로 만들지 않는다.

### D-027 카드 없는 미니멀 UI

제품 화면은 구조적 카드 컨테이너를 정보 계층의 기본 단위로 사용하지 않는다. 자산 등록을 포함한 폼, 목록, 요약, 설정과 빈·오류 상태는 하나의 연속된 페이지 위에서 제목·타이포그래피·여백·정렬·얇은 구분선과 `fieldset`으로 관계를 표현한다. 섹션마다 배경·테두리·radius·그림자를 함께 적용한 박스를 반복하거나 박스 안에 다시 박스를 중첩하지 않는다.

입력·버튼·선택 컨트롤의 경계와 focus ring은 조작성을 위한 것이므로 유지한다. 페이지 위에 실제로 떠야 하는 dialog, sheet, popover, toast와 PWA 갱신 prompt만 별도 표면과 최소한의 elevation을 사용할 수 있다. 빈 상태와 오류 상태도 별도 카드로 만들지 않고 해당 데이터 영역 안의 인라인 문구와 행동으로 표시한다.

휴대폰 floating 하단 dock도 viewport 위에 고정되는 단일 내비게이션 표면으로서 이 예외에 포함한다. 왼·오른쪽·하단 safe area 밖에 12px 이상 간격을 두고, 20px 이상 외곽 radius와 최소한의 그림자만 사용한다. 이 예외를 내용 섹션의 장식성 카드에 확장하지 않는다.

### D-028 자산 종류 우선 선택과 기본 이름

자산 등록·수정은 자산 이름보다 종류를 먼저 선택한다. 자산 종류는 `select`가 아니라 한 화면에서 선택지를 비교할 수 있는 접근 가능한 버튼 그룹으로 제공하고, 선택된 종류는 색뿐 아니라 `aria-pressed`와 명확한 시각 상태로 표시한다. 신규 등록에서 종류 바로 아래에 `자산 이름 (선택)`을 제공하며 상세 수정에서도 바꿀 수 있다.

이름을 입력하면 그 이름으로 저장하고, 비워 두면 선택한 종류명을 실제 저장 이름으로 사용한다. 같은 종류의 기본 이름이 이미 있으면 `계좌 2`, `계좌 3`처럼 사용 가능한 가장 작은 번호를 붙여 반복 등록한다. 자산 종류 자체를 새로 만들거나 이름을 바꾸지 않는다. 직접 입력한 자산 이름은 종류 변경만으로 덮어쓰지 않으며, 사용자가 이름을 지운 경우에만 현재 종류의 사용 가능한 기본 이름으로 돌아간다.

### D-029 입력량에 비례하는 컴팩트 폼

입력 화면은 큰 컨트롤·빈 여백·반복 설명 때문에 실제보다 많은 작업을 요구하는 것처럼 보이지 않아야 한다. 공통 입력과 선택 컨트롤은 모바일 터치 목표를 충족하는 44px을 기본 높이로 사용하고, 연속 필드 간격은 12–16px, 섹션 간격은 20–24px을 기본으로 한다. 모바일 `320–767px`의 거래 입력은 예외 없이 금액 → 날짜 → 분류 → 자산 → 사람 → 내용 순서의 단일 열로 읽는다. 금액을 첫 번째 전체 폭 입력으로 두고 날짜는 다음 독립 행에 두며, 두 control은 같은 전체 폭과 48px 높이를 사용한다. 거래 날짜 trigger는 선택값을 한국식으로 읽기 쉽게 표시하고 모바일에서는 하단 drawer, `768px` 이상에서는 trigger에 붙는 달력을 연다. 달력은 오늘 이동, 월 이동, 키보드 조작, 닫은 뒤 trigger focus 복구를 지원하되 draft와 API에는 기존 `YYYY-MM-DD` 문자열만 유지한다. 단지 화면 폭을 채우기 위해 서로 다른 입력을 반반 나누지 않는다. iPad·데스크톱도 관련 없는 입력은 독립 행과 내용에 맞는 최대 너비를 사용하고, 이체의 보내는 자산 → 받는 자산처럼 한 결정을 함께 비교해야 하는 필드만 충분한 폭에서 병렬 배치한다. 거래 폼의 연속 필드를 두 개씩 임의의 시각 묶음으로 만들거나 그 묶음마다 구분선을 반복하지 않는다.

자산 폼의 종류 선택은 모바일 3열, 큰 모바일 이상 5열을 기본으로 하고 긴 종류명은 버튼 안에서 줄바꿈한다. 신규 등록은 종류·기준일 잔액·잔액 기준일과 유형별 필수 연결 설정을 짧은 흐름으로 보여주고, 상세 수정에서는 소유자인 구성원 한 명을 선택한다. 기준일 잔액·잔액 기준일 입력은 모바일에서 적층하고 `768px` 이상의 충분한 콘텐츠 폭에서만 같은 잔액 기준 맥락의 비대칭 행으로 바꾼다. 데스크톱의 자산·일반 거래 폼은 최대 약 `48rem`, 필드 수가 많은 카드 정정·환불 폼은 최대 약 `52rem` 안에서 의미 기반 grid를 사용한다. 반응형 배치는 하나의 DOM과 CSS로 처리하고 resize·회전 때 draft·focus·query 상태를 초기화하지 않는다. 이 밀도 조정은 원장 posting과 동시성 계약을 바꾸지 않는다.

상세 수정도 `기본 정보`, `소유 표시`, `시작 금액과 날짜` 같은 당연한 묶음을 큰 제목·반복 설명·구분선으로 단계화하지 않는다. 자산 종류부터 메모까지 각 필드 label로 이어지는 하나의 입력 흐름으로 보여주고, semantic `fieldset`·`legend`가 필요해도 일반 label과 같은 시각적 위계로 둔다. 신용카드·체크카드·적금 유형에서만 조건부 전문 입력이라는 맥락 전환을 알리는 짧은 설정 표지와 단일 구분선을 허용한다.

일반 거래의 약 `48rem`은 입력 열 자체의 읽기 폭이다. `1024px` 이상의 전체 거래 작업 영역은 최대 약 `74rem`으로 늘려 입력 열과 18~20rem 요약 rail을 나란히 둔다. 요약은 같은 draft를 읽기만 하고 작성 control과 저장 행동은 중복하지 않는다.

### D-030 빠른 자산 등록과 상세 설정 분리

모든 자산의 신규 등록 화면은 `자산 종류`, 선택 입력인 `자산 이름`, `기준일 잔액`, 사용자가 선택하는 `잔액 기준일`을 받는다. 대출은 금액 label을 `기준일 대출 잔액`으로 보여주되 기존 signed 원장 규칙을 유지해 사용자가 음수로 입력했을 때 부채로 기록한다. 이름을 비운 경우만 종류 기반 기본 이름을 사용하고, 소유는 현재 멤버의 개인 소유, 메모는 없음으로 저장한다. 이 기본값은 권한이나 거래 주체를 바꾸지 않으며 등록 후 자산 목록에서 해당 자산을 열어 모두 수정할 수 있다. 등록 성공 시 상세 입력을 연이어 요구하지 않고 자산 목록으로 돌아간다.

신용카드 신규 등록은 정확한 명세와 결제 예정일 계산을 위해 정산일, 결제 월·일, 결제 계좌를 추가로 필수 입력한다. 체크카드는 실제 지출 posting이 차감될 결제 계좌를 필수 입력한다. 적금의 자동이체는 선택 설정이며, 사용하지 않으면 계좌와 날짜 없이 적금만 등록한다. 자동이체를 사용하면 같은 설정 안의 계좌와 달력일을 모두 입력해야 하고 둘 중 하나만 저장하지 않는다. 적금의 금액·시작일·catch-up 정책이 확정되기 전에는 설정을 저장해도 자동 거래를 생성하지 않는다. 연결 계좌는 같은 가계부의 결제 가능한 활성 자산만 허용한다. 신용카드 자동 정산은 제공하지 않고 API 호환 필드는 항상 `false`다(D-069). 연결 가능한 계좌가 없으면 작성 중인 입력을 보존한 채 계좌 등록 행동을 제공한다. 모든 생성 응답은 현재 작성 세션의 목록 cache를 갱신하고, 다른 세션은 기존처럼 진입·focus·수동 새로고침에서 확인한다.

### D-031 고정 자산 종류와 기타의 현금성 처리

자산 종류는 가계부마다 제공되는 고정 시스템 종류만 사용하고 사용자가 새 종류를 만들거나 종류 표시명을 바꾸는 기능은 제공하지 않는다. `기타`는 `현금`과 같은 `STANDARD` 동작과 결제 계좌 비대상 속성을 가진 현금성 자산으로 취급한다. 사용자는 `기타` 자산의 개별 이름을 자산 등록과 상세에서 자유롭게 지정할 수 있으므로 별도 사용자 정의 종류는 필요하지 않다. 기존 사용자 정의 종류에 연결된 자산은 마이그레이션에서 같은 가계부의 `기타`로 재분류하되 자산 이름, 거래, posting과 잔액은 보존한다. `BANK` 시스템 코드의 사용자 표시명은 `계좌`, `SAVINGS`는 `적금`으로 한다. 표시명 변경은 기존 사용자가 지정한 `asset.name`을 덮어쓰지 않는다.

### D-032 신규 가계부 기본 자산

신규 가계부를 생성하는 트랜잭션에서 `현금`, `계좌`, `신용카드`, `체크카드` 자산을 하나씩 만든다. 모두 생성자의 개인 소유 marker, 한국 시간대 기준 가계부 생성일을 잔액 기준일, 기준일 잔액 0원으로 시작하며 0원 `OPENING_BALANCE` posting은 만들지 않는다. 신용카드는 14일 정산·25일 다음 달 결제, 기본 계좌 연결, 자동 정산 끔으로 시작하고 체크카드도 기본 계좌를 결제 계좌로 연결한다.

기본 자산은 별도의 영구 marker가 아닌 일반 자산으로 등록되어 모든 구성원이 이름·소유·금액·설정을 수정할 수 있고, 활성 자산 50개 한도에 포함된다. 기존 가계부에는 자산을 소급 생성하지 않고 `BANK` 종류 표시명만 `계좌`로 바꾼다. 초대 수락은 기본 자산을 다시 생성하지 않는다.

기본 계좌를 포함해 다른 카드의 결제 계좌나 적금 자동이체 계좌로 참조되는 자산은 해당 연결을 먼저 옮기기 전에 결제 계좌 비대상 유형으로 변경할 수 없다.

### D-033 연결 계좌의 인라인 등록

신용카드·체크카드·적금 등록 중 연결 가능한 계좌가 없으면 별도 탭이나 별도 자산 등록 route로 이탈시키지 않고 현재 폼 위에 `계좌 등록` dialog를 연다. dialog는 모바일·설치형 PWA·iPad·데스크톱 모두 입력 콘텐츠 높이에 맞춘 폭이 제한된 중앙 overlay로 표현하고, 콘텐츠가 viewport를 넘을 때만 최대 높이를 제한해 내부를 스크롤한다. 같은 DOM·필드·API 계약을 사용하며 부모 자산의 이름·금액·날짜·유형별 설정 draft는 dialog를 열고 닫거나 viewport가 바뀌어도 유지한다.

계좌 dialog는 선택 이름, 기준일 잔액, 잔액 기준일만 받고 현재 사용자의 개인 소유·메모 없음인 `BANK` 자산을 기존 `POST /api/assets`와 idempotency 계약으로 생성한다. 기준일 잔액은 실제 `0` 값으로 미리 채우지 않고 빈 입력에 `0` placeholder만 보여주며, 빈 채로 저장하면 0원으로 정규화한다. 0원이 아닌 경우에만 사용자가 원 단위 정수를 입력한다. 성공 응답은 현재 자산 목록 cache에 반영하고 방금 만든 계좌를 부모 폼의 결제 계좌 또는 자동이체 계좌로 즉시 선택한 뒤 dialog를 닫는다. 실패하면 계좌 입력을 유지한다. 취소·`Escape`·브라우저 뒤로 가기는 부모 route를 이탈하지 않고 dialog만 닫으며, 닫은 뒤에는 `계좌 등록` trigger로 focus를 복귀시킨다. 새 탭은 열지 않고 API·금융 데이터의 service worker cache나 offline mutation queue도 만들지 않는다.

연결 가능한 계좌가 이미 한 개 이상 있어도 신용카드·체크카드·적금 설정에는 `계좌 추가` 행동을 항상 제공한다. 새 계좌를 만든 뒤에는 기존 선택을 덮어쓰고 방금 만든 계좌를 현재 설정의 결제 계좌 또는 자동이체 계좌로 선택하되, 부모 자산 자체는 사용자가 최종 저장하기 전까지 수정하지 않는다.

### D-034 자산 현황과 현재 자산·카드 결제 일정

자산 첫 화면은 활성 자산의 단순한 단일 목록이 아니라 공동 가계부의 자산 현황을 한눈에 읽는 화면이다. 사용 종료 자산까지 포함한 양수 잔액 합계인 `총자산`과 음수 잔액 절댓값 합계인 `총부채`의 차이인 `순자산`을 가장 큰 핵심 값으로 한 번만 보여주고, 총자산·총부채는 그 계산 근거로 한 단계 작게 둔다. 활성 신용카드는 아직 결제되지 않은 명세를 실제 결제일 순서로 읽어 `가장 가까운 결제일·금액 | 그다음 결제일·금액`으로 보여준다. 결제일이 지난 미결제 명세도 누락하지 않고 먼저 보여주며 사용 종료 카드는 자동 결제가 중단되므로 합계에서 제외한다.

활성 자산은 고정 시스템 종류 코드에 따라 `자금(CASH, OTHER, BANK, SAVINGS)`, `카드(CREDIT_CARD, DEBIT_CARD)`, `투자(INVESTMENT)`, `대출(LOAN)`, `보험(INSURANCE)`으로 묶고 빈 그룹은 숨긴다. `자금`은 현금·기타·계좌·적금의 현재 가용 자금을 함께 읽는 화면 용어이며 영속 종류나 behavior 이름은 아니다. 마이너스 통장은 별도 종류가 아니라 현재 잔액이 음수인 `BANK` 계좌다. 모든 viewport에서 그룹은 두 열로 나누지 않고 고정 순서의 한 열로 이어지며, 그룹명은 실제 자산 이름과 현재 금액보다 작은 탐색용 표지로만 보여준다. 서로 다른 그룹의 시작에는 전체 폭 1px 기준선을 두고, 그룹 머리와 자산 행의 내부 구분선은 그보다 옅게 표현해 배경·둥근 모서리·그림자 없이도 부류의 경계를 식별하게 한다.

개별 자산 행은 자산명과 금액을 우선하고 종류·소유자를 독립된 고정 metadata 열로 만들지 않는다. 종류명과 같은 이름 또는 `종류명 + 양의 정수` 기본 이름은 종류를 생략하고, custom 이름에만 작은 muted 종류를 자산명 아래 보조행에 붙인다. 전체 보기에서는 현재 사용자를 `나`, 다른 구성원을 같은 보조행에 표시하지만 소유자별 보기에서는 이미 선택한 소유 맥락을 반복하지 않는다. 모바일에서는 자산명과 필요한 metadata를 말줄임표 없이 자연스럽게 감싸 전체 이름을 읽게 하고, iPad 이상에서만 각 줄에 제한적 말줄임을 허용한다. 이름·부가정보·금액이 서로 경쟁하지 않도록 부가정보는 자산명과 같은 한 줄에 끼워 넣지 않는다. 화면에서 생략한 경우에도 링크의 접근 가능한 이름은 전체 종류와 소유자를 보존한다.

`자금` 그룹은 자산별 `currentBalanceWon`을 부호 그대로 가장 오른쪽 한 열에 표시하고, 그룹 머리의 `현재 합계`도 같은 signed 합계로 계산한다. 그룹 `현재 합계` 금액은 16px을 유지하고 개별 자산의 `현재 자산` 금액은 한 단계 작은 14px로 표시해 합계와 항목의 위계를 구분한다. 계좌 잔액이 음수면 이름과 관계없이 `-금액`으로 보여주며 `부채` 열이나 절댓값 변환을 사용하지 않는다. 투자·대출·보험은 기존처럼 현재 잔액의 부호에 따라 자산·부채 의미를 유지한다.

카드 그룹과 모든 카드 행은 `부채`, `현재 부채`, `카드 부채`를 표시하지 않는다. 신용카드 행은 `M월 d일 결제 | M월 d일 결제` 두 열로 가장 이른 두 미결제 결제일과 금액을 표시하고, 전체 카드 그룹 머리는 카드별 첫 번째·두 번째 결제 금액을 각각 `가까운 결제 합계 | 그다음 결제 합계`로 합산한다. 그룹 합계는 16px semibold, 개별 카드 행 금액은 14px semibold로 표시한다. 체크카드나 미결제 명세가 없는 카드는 가짜 날짜와 0원 두 열 대신 `결제 예정 없음`으로 표시한다. 480px 미만에서는 카드 자산 정보 아래에 두 열을 두고, 그 이상에서는 자산 정보와 두 금액을 같은 행에 정렬한다. 자금·투자·대출·보험의 단일 잔액 rail은 이름 오른쪽에 둔다. DOM 읽기 순서는 항상 자산 정보, 가까운 결제, 그다음 결제다. 서로 다른 자산 분류 사이에는 모바일 24px, iPad·데스크톱 32px의 빈 여백을 두며 구조적 카드 컨테이너나 장식용 그래프를 만들지 않는다. 금액은 중간에서 줄바꿈하거나 임의 축약하지 않는다.

`GET /api/assets`는 기본적으로 활성 자산을 반환하고 `status=ARCHIVED/ALL`로 보관 또는 전체 자산을 조회한다. 그룹 분류의 source of truth인 `systemCode`, 상태와 함께 카드별 `nearestCardPaymentDueOn/Won`, `followingCardPaymentDueOn/Won`을 반환한다. 기존 월 단위 두 필드는 배포 중 구버전 PWA 호환을 위해 당분간 함께 반환한다. 백엔드는 `card_statement_forecast`의 `OPEN/FINALIZED` 양수 미결제액을 카드·결제일별로 먼저 합치고 날짜순 첫 두 결제일과 기존 월 합계를 한 번의 batch query로 계산한다. 프론트는 전체 목록에서 순자산과 카드 결제 합계를, 활성 목록에서 그룹 합계와 개별 활성 행을 선형 계산하며 별도 영속 합계나 새 cache 계층은 두지 않는다.

### D-035 설정 기반 버튼형 공동 분류 관리

공동 수입·지출 분류 관리는 가계부 설정의 독립 `분류 설정` 메뉴에서 제공한다. 수입·지출 방향은 버튼으로 전환하고, 현재 방향의 분류는 반복 행이나 분류마다 노출되는 수정·삭제 아이콘 대신 최소 44px 높이의 compact 버튼 모음으로 보여준다. 한 분류를 선택하면 그 분류의 전체 이름, 연결 거래 수, 이름 수정과 조건부 삭제 행동만 별도 관리영역에 표시한다. 기본 `기타`도 선택하고 이름을 바꿀 수 있지만 삭제 행동은 노출하지 않는다.

모바일·iPad·데스크톱은 같은 버튼 DOM과 category ID 선택 상태를 유지하고 가용 폭에 따라 열 수만 바꾼다. 긴 이름은 버튼 안에서 최대 두 줄로 제한하되 접근 가능한 이름과 선택 관리영역에는 전체 이름을 보존한다. 선택 상태는 `aria-pressed`와 테두리·배경·굵기를 함께 사용하고, viewport 변경으로 선택·추가/수정 draft·focus·TanStack Query 상태를 초기화하지 않는다. 기존 category version 충돌, fallback 이동, cache invalidation과 다른 세션의 focus 재조회 계약은 바꾸지 않는다.

각 분류에는 이름 선택과 분리된 최소 44px 순서 이동 핸들을 두고, 포인터 드래그·터치 드래그와 키보드 이동으로 현재 수입 또는 지출 방향 안의 순서를 바꾼다. 한 번의 이동은 현재 방향의 활성 분류 전체 ID와 version을 보내 원자적으로 저장하며, 다른 구성원이 추가·이름 변경·삭제·순서 변경을 먼저 수행했다면 `412`로 전체를 거부하고 최신 순서를 다시 보여준다. 성공한 정렬은 설정뿐 아니라 거래 입력 분류 picker에도 같은 순서로 반영한다. `sort_order`가 영속 source of truth이며 기본 `기타`도 사용자가 이동할 수 있고, 새 분류는 현재 `기타` 바로 앞에 추가한다.

거래 기록의 분류 필드는 native select 대신 하나의 반응형 picker를 사용한다. trigger를 누르면 모바일에서는 화면 아래에서 여는 drawer, iPad·데스크톱에서는 compact dialog로 같은 분류 버튼 DOM을 보여준다. 마지막 `항목 추가` 버튼은 picker 안에서 공동 분류 이름 입력으로 전환하고 기존 `POST /api/categories` 응답을 해당 방향 목록 cache에 반영해 새 분류를 즉시 선택한다. 추가 실패·오프라인에는 이름과 거래 draft를 보존하며 viewport 변경으로 drawer/dialog, 선택값, 입력값과 focus를 초기화하지 않는다.

### D-036 자산 현황의 소유자별 보기

자산 현황은 현재 로그인한 구성원의 자산을 기본으로 보여주고 `전체 · 각 구성원` 소메뉴로 소유 marker별 현황을 볼 수 있다. 선택한 범위의 순자산·총자산·총부채는 활성·사용 종료 자산을 포함하고, 가장 가까운 두 카드 결제 예정 금액과 그룹 합계·개별 행은 활성 자산만 사용한다. 활성 `n/50`은 필터와 관계없이 가계부 전체 활성 자산 수를 유지한다.

선택값은 `/assets`의 `owner` query parameter를 source of truth로 사용해 새로고침·PWA·viewport 변경에도 유지한다. query가 없거나 유효하지 않으면 현재 사용자 보기를 기본으로 해석한다. 사용자가 전체를 선택하면 `all`, 구성원은 `member:<memberId>`를 사용하며 표시명은 URL에 넣지 않는다. 현재 사용자가 API 응답에 없는 비정상 상태에서만 전체를 안전한 fallback으로 사용한다. 활성·보관 조회 결과를 프론트에서 선형 필터링하므로 소유자별 API·영속 합계·별도 cache는 추가하지 않는다. 소유자 선택은 visible 소제목·필터 상자 없이 선택 항목의 하단선만 남기는 text subnav로 요약과 바로 이어진다. 모바일에서는 subnav 자체만 한 줄 가로 스크롤하고 이름을 말줄임하지 않아 여러 줄이 실제 자산을 아래로 밀지 않게 한다. 활성 개수·새로고침도 별도 전체 폭 행을 만들지 않는다. 결과가 없으면 전체 가계부의 첫 자산 onboarding과 구분되는 짧은 빈 상태와 `전체 자산 보기` 행동만 제공한다.

### D-037 카드 명세 선결제와 자동 정산

> 아래는 기존 명세 API와 과거 결제 이력의 계약이다. 자동 실행·예약 재생성은 D-069로 폐기했고, 현재 카드 상세 결제는 D-069를 따른다.

신용카드 자산 상세를 카드 명세의 단일 진입점으로 사용한다. 기간이 제한된 cursor 목록과 명세 상세에서 `청구 원금 · 결제 완료 · 남은 결제`, 실제 출금 계좌와 결제 기록을 보여주며, 완료 내역은 사용자가 명시적으로 펼칠 때 조회한다. 개별 카드 구매 화면은 귀속 명세 링크만 제공하고 선결제 행동을 중복하지 않는다.

부분·복수 선결제는 서버 미리보기 후 기록한다. 미리보기 token은 명세 version·남은 금액·요청 금액·현재 결제 계좌·`Asia/Seoul` 기준 서버 적용일을 묶고, apply 시 하나라도 달라졌으면 `412 CARD_STATEMENT_PREVIEW_STALE`로 전체 저장을 거부한다. 계좌의 파생 잔액은 다른 정상 거래와 동시에 바뀔 수 있으므로 stale 기준에 넣지 않고 apply 시 최신 잔액을 반환한다. 프론트는 `412`에도 사용자의 금액 draft를 보존하고 최신 명세로 다시 미리보기를 받아야 기록할 수 있다.

자동 정산 schedule은 카드의 자동 정산 사용 여부와 결제 계좌 설정에 맞춰 미처리 명세만 동기화한다. worker는 `scheduled_on <= 오늘`인 schedule을 작은 트랜잭션으로 따라잡고 원래 예정일을 거래일·결제일로 기록한다. statement 행 잠금, idempotency와 unique 제약으로 선결제 합계가 남은 금액을 넘거나 정규 결제가 중복되지 않게 한다. 전액 선결제 후 구매 정정으로 미결제액이 다시 생기면 결제일 전은 `OPEN`, 결제일 이후는 `FINALIZED`로 재개하고 schedule을 복구한다. 결제 계좌 잔액이 부족해도 전액 posting해 음수 잔액을 허용하며 기술 실패만 재시도한다.

### D-038 월간 MVP 통계 조회와 표현

통계 첫 진입은 `Asia/Seoul`의 이번 달과 현재 구성원의 경제활동이다. `GET /api/statistics/monthly`는 선택 월 반개구간의 수입·지출·순액과 수입/지출별 분류 순금액, 선택 월이 속한 연도의 1월부터 12월까지 월별 수입·지출·순액을 같은 필터로 반환한다. 일별 추이 SQL과 화면은 제거한다. 이미 캐시된 이전 PWA 앱 셸이 새 버전 갱신 prompt까지 렌더링할 수 있도록 `dailyTrend: []`만 deprecated 호환 필드로 한 배포 주기 이상 유지하고 새 클라이언트는 사용하지 않는다. 통계 상단에서 거래 주체를 `나 · 각 구성원 · 모두` 중 하나로 항상 선택하고, 선택 자산의 현재 소유 marker와 공동 분류는 별도 세부 필터로 각 한 개씩 선택해 AND로 적용한다. 거래 주체는 작성자가 아니라 `performed_by_member_id`, 자산 소유자는 posting 계좌가 아니라 거래의 `primary_asset_id`를 기준으로 한다. 월과 필터는 `/statistics` search parameter에 보존한다. `member` query가 없거나 유효하지 않으면 현재 구성원, `member=all`은 전체, 다른 구성원 UUID는 해당 구성원으로 해석한다.

소비 통계 source of truth는 삭제되지 않은 `INCOME`과 `EXPENSE`만 포함하는 `ledger_financial_activity`다. 신용카드 구매는 구매일의 양수 지출, 실제 환불은 환불일의 음수 지출이고 일반 이체·카드 정산·선결제·최초 금액 조정은 포함되지 않는다. 선택 월의 합계·분류는 한 달 반개구간 `GROUPING SETS` SQL로, 연간 흐름은 같은 연도의 반개구간과 `date_trunc('month')` group으로 집계한다. 두 bounded query는 read-only repeatable-read snapshot에서 실행해 선택 월 합계와 같은 달의 연간 막대가 어긋나지 않게 하며, 상시 누적 합계·materialized view·Redis cache를 두지 않는다.

아래 초기 시각화는 D-070의 통합 화면과 가로 막대로 대체한다. 화면은 장식성 KPI 카드를 사용하지 않는다. 얇은 구분선 위의 금액 요약, 지출 기본·수입 전환형 분류 비중, 해당 연도의 12개월 수입·지출 grouped bar와 원 단위 월별 목록을 같은 DOM으로 재배치한다. 연간 막대는 수입·지출 의미색, 월 label과 정확한 `월별 금액 목록`을 함께 제공하고 선택 중인 달을 글자 굵기·색으로 표시한다. 모바일에서도 12개월을 한 화면 폭에 유지하며 페이지 가로 스크롤이나 별도 chart dependency를 만들지 않는다. 분류 비중은 production chart dependency 없이 native SVG 원형 차트를 함께 제공하되 정확한 signed 금액·비율 행을 source of truth로 유지한다. 차트는 최대 6개 조각으로 제한해 분류가 6개 이하면 모두 표시하고, 7개 이상이면 순금액 상위 5개와 나머지 합계 한 조각을 표시한다. 조각은 수입·지출 의미색에 종속하지 않고 돈독의 저채도 톤을 맞춘 녹색·테라코타·청색·황동·자주·올리브 팔레트를 순서대로 사용하며 불투명도 차이만으로 구분하지 않는다. 같은 조각색은 분류 행의 작은 표지와 연결하고 정확한 이름·금액·비율을 항상 함께 제공한다. 환불 때문에 선택 방향의 전체 합계 또는 분류 순금액이 0 이하라면 왜곡된 비율·원형 차트·분류 막대를 만들지 않고 signed 금액과 환불 반영 안내만 보여준다. 통계는 모바일의 `홈 · 기록 · 자산 · 통계 · 설정` dock과 iPad·데스크톱의 네 데이터 메뉴 안에서 동일한 의미로 접근한다.

### D-039 가계부 전체 삭제와 세션 복귀

개인 나가기 대신 모든 구성원이 같은 권한으로 가계부 전체를 삭제할 수 있다. 설정의 낮은 위계 파괴적 작업에서 `가계부 삭제` 문구를 직접 입력하고, dialog를 열 때의 가계부 `ledgerId`와 `version`을 함께 보내 서버가 현재 membership과 행 잠금 뒤 재검증한다. `expectedLedgerId`는 오래 열린 탭의 기존 가계부가 삭제된 뒤 새 가계부가 생성된 ABA 경합에서 새 가계부를 잘못 삭제하지 않게 한다. 멤버 참여와 초대 발급·취소처럼 가계부 공유 구조가 바뀌면 `ledger_book.version`을 증가시켜 열려 있던 삭제 확인을 stale로 만든다. 삭제는 `ledger_book`과 모든 하위 멤버십·초대·자산·분류·거래·카드·audit 데이터를 한 트랜잭션에서 물리 삭제한다.

사용자 계정과 Spring 로그인 세션은 삭제하지 않는다. 요청한 브라우저는 가계부 전용 TanStack Query cache를 비우고 즉시 가계부 시작·초대 코드 화면으로 돌아간다. 다른 구성원 브라우저는 다음 가계부 API의 `404 LEDGER_NOT_FOUND` 또는 현재 가계부 재조회에서 같은 cache를 비우되 로그인 상태를 유지한다. 삭제 전 가계부 URL을 다시 열어도 삭제 데이터를 노출하지 않는다.

### D-040 PostgreSQL 일일 백업과 격리 복구 기반

Mac mini의 사용자 launchd가 매일 운영 Compose의 정확한 working directory·config file label을 확인한 뒤 PostgreSQL 컨테이너 자체의 `pg_dump`로 custom zstd archive를 만든다. 저장소 밖의 사용자 전용 0700 경로에 0600 dump·checksum·manifest를 partial bundle로 쓰고 archive list와 SHA-256 검증 뒤에만 원자적으로 완료 이름으로 바꾼다. 완료 UTC 시각부터 30×24시간이 지난 bundle은 성공한 백업 뒤 rotation하며 partial, symlink와 backup root 밖 대상은 자동 삭제하지 않는다. 환경변수와 row 내용은 manifest·log에 넣지 않는다.

복구 drill은 live DB·Compose·운영 volume·`.env`에 의존하지 않는다. checksum으로 보호한 manifest의 PostgreSQL image ID·repository digest, 원본 database byte 크기와 Flyway version을 현재 release와 대조하고, 원본 DB 크기의 3배+1GiB 여유를 확인한 뒤 포트·network가 없는 고유 throwaway PostgreSQL volume에 single transaction으로 복원한다. Flyway history, 필수 table·view·index, 정확한 정의의 V5 legacy `NOT VALID` check 외 검증 제약, 21개 ledger cascade FK와 대표 orphan 부재를 확인한다. 자기 run ID label의 임시 container·volume과 maintenance lock이 실제로 제거되어야 성공한다.

이 로컬 daily·restore 기반은 archive의 구조적 복구 가능성을 보장하지만 그 자체로 disaster cutover를 승인하지 않는다. 삭제 전 백업에서 가계부가 재등장하지 않게 할 off-device 삭제 내구성·복구 지점 정책과 weekly client-side 암호화 복제 위치·키 보관은 Q-036~Q-038 결정 뒤 연결한다. 해당 절차 전에는 denylist 없는 drill이 명시적 경고와 함께 구조 검증만 통과하며, 실제 승격 때는 복원된 session·인증/재설정 token·미사용 초대도 무효화한다.

### D-041 일반 이체의 계좌·적금·주식 계좌 경계

사용자가 기록·수정하는 일반 이체의 출발·도착 후보는 같은 가계부의 활성 `BANK` 계좌, `SAVINGS` 적금, `INVESTMENT` 주식 계좌 자산을 허용한다. 이들 사이의 납입·인출·자금 이동은 출발 `-amount`, 도착 `+amount`의 동일한 일반 이체이며 수입·소비 지출에는 포함하지 않고 D-068의 저장된 목적에 따라 납입·회수 통계에 반영한다. 자산 소유자는 권한이 아닌 marker이므로 현재 사용자와 다른 구성원 소유 자산을 구분 없이 출발·도착으로 조합할 수 있고, 선택기에는 자산 이름·종류와 `나`·구성원 이름 소유 표시를 함께 보여준다. 이체를 실행한 사람인 `performed_by_member_id`는 두 자산의 소유자와 독립적으로 선택한다. 음수 잔액 계좌도 같은 `BANK`이므로 후보에 포함하며, 현금·카드·대출 등 다른 물리 유형은 일반 이체 선택기에 노출하지 않고 API 직접 요청도 기존 호환 오류 코드 `400 TRANSFER_ACCOUNT_OR_SAVINGS_REQUIRED`로 거부한다. 출발과 도착은 서로 달라야 하며 활성 계좌·적금·주식 계좌 자산이 합쳐 두 개 미만이면 draft를 유지한 채 추가 등록이 필요함을 알리고 저장을 막는다. 적금 자동이체 설정은 이 일반 이체를 자동 생성할 향후 정책과 별개이며 수동 이체 가능 여부를 제한하지 않는다. 이 경계는 내부 `CARD_SETTLEMENT`·`CARD_PREPAYMENT` 등 시스템 이체에는 적용하지 않는다.

### D-042 shadcn과 선택 컴포넌트 기준

프론트엔드 공통 UI는 최신 shadcn의 Base UI 기반 `base-nova` 스타일과 돈독 디자인 토큰을 사용한다. 기능 화면이 HTML control이나 overlay를 직접 꾸미지 않고 `components/ui`의 Button, Input, Textarea, Label, NativeSelect, Checkbox, Switch, RadioGroup, Dialog를 조합하며, 링크형 Button도 Base UI `render` 합성을 사용한다. 짧고 검색이 필요 없는 단일 선택은 모바일의 OS 선택 경험과 성능을 유지하는 `NativeSelect`, 분류처럼 즉시 추가·다중 상태·반응형 배치가 필요한 선택은 동일한 draft를 유지하는 Dialog 기반 picker, 후보가 길어 검색이 실제로 필요해질 때는 Combobox를 사용한다. 모바일과 데스크톱 때문에 제어 DOM을 이중 구현하지 않으며 overlay는 Base UI의 focus trap, Escape, outside press를 브라우저 뒤로가기 계약과 함께 검증한다.

거래 주체처럼 소수의 사람 중 한 명을 고르는 선택은 native select를 사용하지 않는다. Base UI `RadioGroup`에 한 글자 식별자·전체 표시명·현재 사용자 `나` 표식을 가진 compact person option을 조합하며, 선택 상태는 radio 의미와 테두리·배경·굵기로 함께 표시한다. 옵션은 최소 44px 조작 영역을 유지하고 같은 DOM이 가용 폭에 따라 자동 줄바꿈하며 거래 종류 변경·viewport 변경으로 선택값이나 draft를 초기화하지 않는다.

자산 소유자와 수입·지출·이체의 사람을 표시하거나 선택하는 곳에는 공통 구성원 avatar를 이름과 함께 사용한다. avatar는 표시명의 첫 grapheme을 사용하고 구성원 ID에서 결정되는 저채도 색을 유지해 같은 사람을 화면마다 빠르게 식별하게 한다. 현재 사용자의 `나`와 전체 표시명은 그대로 남기며 avatar의 글자나 색만으로 사람·소유 의미를 전달하지 않는다.

### D-043 원화 금액 입력 표현

사용자가 작성하는 모든 원화 금액은 공통 `MoneyField`를 사용한다. 입력 중 천 단위 구분 기호를 즉시 표시하고 우측 정렬한 큰 tabular 숫자와 고정 `원` 단위로 일반 숫자 입력과 시각적으로 구분한다. 표시값과 무관하게 폼 draft·API에는 콤마 없는 정수 문자열·정수만 전달하며 소수는 허용하지 않는다. 자산 기준일 잔액은 빈 값이면 0원이고 음수 부호를 허용하며, 거래·환불·선결제 금액은 양수 입력만 허용한다. viewport 변경·오프라인·충돌에도 원본 draft와 focus를 보존한다.

공통 기본은 56px 높이와 20~24px 숫자를 유지하되, 거래 기록에서는 연관된 날짜 field와 한 줄로 읽히도록 금액만 48px 높이·18~20px로 compact 조합한다. `원`, 천 단위 구분, semibold·tabular·우측 정렬은 유지해 일반 숫자 입력과의 구분은 잃지 않는다.

### D-044 운영 PostgreSQL의 LAN 전용 관리자 접근

DBeaver 같은 운영자 도구는 같은 신뢰 LAN에서만 운영 PostgreSQL에 직접 연결할 수 있다. Compose의 안전한 기본 bind는 `127.0.0.1:15432`이며 Mac mini 운영 환경에서만 비공개 운영값 `DONDOK_DB_BIND_HOST:DONDOK_DB_HOST_PORT`로 명시적으로 덮어쓴다. `0.0.0.0`, IPv6 wildcard와 bare host port bind를 금지하고 공유기에는 DB 관리 포트나 PostgreSQL 포트포워딩을 만들지 않는다. DBeaver는 애플리케이션 DB owner가 아니라 강한 별도 비밀번호, 접속 수 제한과 public schema 조회 권한만 가진 별도 읽기 전용 계정을 사용하며 실제 계정명·DB 이름·접속 정보는 비공개 운영 문서에서만 관리한다. 이 예외는 WAN 공개를 허용하지 않으며 Mac mini의 LAN 주소가 바뀌면 운영 환경값과 접속 설정을 함께 갱신한다.

### D-045 일일 변경 기반 운영 배포

private 배포 workflow는 매일 `03:00 Asia/Seoul`에 한 번 실행해 CI가 성공한 최신 public `main` SHA를 확인한다. Mac mini의 `$DONDOK_STATE_DIR/current-revision`과 같으면 checkout·백업·빌드·Compose·외부 smoke를 모두 건너뛰고, 다른 경우에만 기존 백업·복원 drill·health·rollback 계약으로 배포한다. 사용자가 긴급 즉시 배포를 명시적으로 요청한 경우에만 `workflow_dispatch`로 같은 절차를 바로 실행하며 임의 branch·임의 SHA·CI 미통과 revision은 허용하지 않는다. `DEPLOYMENT_ENABLED=true`가 정상 자동 운영 상태이고 `false`는 예약과 수동 배포를 함께 막는 emergency kill switch다. 예약과 수동 실행이 겹치면 단일 production concurrency group으로 직렬화한다.

### D-046 6자리 직접 초대 코드와 첫 진입 선택

가계부가 없는 첫 화면은 `초대 코드를 받으셨나요?`라는 한 질문 아래 `바로 시작하기`와 `초대 코드 입력하기` 두 행동만 보여준다. 코드 입력은 별도 참여 화면에서 수행해 새 가계부 생성과 기존 가계부 참여를 한 폼에 섞지 않는다.

직접 입력 코드는 사람이 전달하기 쉬운 숫자 6자리로 발급한다. 공유 URL에는 같은 짧은 값을 넣지 않고 별도의 고강도 token을 사용하며, 두 값은 한 invitation을 가리키되 각각 SHA-256 digest만 저장한다. `direct_code_digest` DB unique와 발급 충돌 재시도로 동시 발급 중복을 막고, 짧은 코드 미리보기·수락은 로그인 사용자별 10분 20회로 제한한다. V17 이전 초대는 기존 digest를 `link_token_digest`로 보존해 발급 당시 URL과 긴 직접 코드를 만료 전까지 계속 사용할 수 있다.

### D-047 사용자 선택 수입·지출 집계 제외

모든 사용자 수입·지출은 거래별로 `수입에 포함하지 않기` 또는 `지출에 포함하지 않기`를 선택할 수 있다. 선택해도 posting과 자산 현재 잔액, 카드 charge·명세·환불 보정은 평소와 동일하게 반영하고, 월간 달력 합계와 통계 합계·분류·연간 흐름에서만 제외한다. 일반 이체·카드 정산·선결제에는 수입·지출 집계 제외 선택을 노출하지 않는다. 일반 이체는 D-068의 목적으로 납입·회수 통계 포함 여부를 정한다.

제외된 거래도 일별 원장과 상세에는 `집계 제외` 상태로 남겨 사용자가 다시 찾고 일반 수입·지출은 수정할 수 있게 한다. 신용카드 구매 정정과 실제 환불도 각각 같은 선택을 저장하며, 새 환불은 원 구매의 선택을 기본으로 이어받되 사용자가 환불 거래별로 바꿀 수 있다. 기존 거래와 필드를 생략한 이전 클라이언트 요청은 모두 집계 포함으로 해석한다.

### D-048 홈 원장의 구성원별 보기

홈의 월간 달력·월 합계·날짜 상세·일별 원장은 같은 거래 주체 필터를 공유한다. 첫 진입은 로그인한 현재 구성원의 기록이 기본이며 `나 · 각 구성원 이름 · 모두` compact 선택으로 전환한다. 구성원별 보기는 작성자가 아니라 `performed_by_member_id`를 기준으로 수입·지출·일반 이체·카드 정산·선결제 원장 행을 제한한다. 월간 달력의 수입·지출 합계는 같은 구성원의 집계 포함 수입·지출만 계산하고, 카드 정산·선결제는 별도 `카드결제` 금액으로 표시한다(D-062). `모두`에서는 모든 구성원의 기록을 표시한다.

선택은 홈 URL의 `member` query에 보존한다. query가 없거나 현재 가계부 구성원이 아닌 값이면 현재 구성원으로 해석하고, 다른 구성원은 member UUID, 전체는 `member=all`로 명시한다. 월 이동·월간/일별 전환·날짜 상세·새로고침·viewport 변경에도 같은 선택을 유지한다. 통계도 D-014에 따라 같은 선택 의미와 현재 구성원 기본값을 사용한다.

### D-049 일반 지출의 신용카드 구매 전환

사용자가 계좌·현금·체크카드 등으로 잘못 기록한 일반 `EXPENSE`는 일반 거래 수정 화면에서 결제 자산을 신용카드로 바꿀 수 있다. 거래 유형은 지출로 유지하고 일시불·할부 수를 함께 받아, 기존 posting의 잔액 효과를 되돌린 뒤 카드 posting, 구매 시점 billing snapshot, 회차별 charge, 명세와 자동 결제 schedule을 한 DB 트랜잭션에서 만든다. 잔액 기준일 이전 구매를 카드 명세에 다시 청구하지 않는 기존 규칙도 동일하게 적용한다.

이 전환이 성공한 순간 응답과 이후 조회의 `managementType`은 `CARD_PURCHASE`다. 그 뒤의 금액·날짜·카드·할부 변경은 이미 생성된 명세와 결제를 함께 맞춰야 하므로 일반 수정·삭제를 막고 기존 `기록 정정`·`환불 처리` 흐름만 사용한다. 즉 오류 메시지는 이미 카드 charge가 있는 거래에만 적용하며, 신용카드를 새 결제 자산으로 고르는 최초 전환을 거부하지 않는다.

### D-050 반응형 자산 선택기

거래의 결제·입금 자산, 이체의 보내는·받는 자산, 카드 구매 정정의 결제 카드, 신용·체크카드와 적금의 연결 계좌는 native select 대신 하나의 공통 `AssetPicker`를 사용한다. 모바일 `320–767px`에서는 safe area 위의 하단 drawer, iPad·데스크톱에서는 trigger에 붙는 compact popover로 같은 option DOM과 draft를 보여준다. 모바일 drawer 외곽은 동적 viewport에 비례한 일정 높이를 유지하고 종류별 후보 수가 달라져도 위쪽 위치와 닫기 버튼이 움직이지 않으며, 넘치는 후보만 내부 목록에서 스크롤한다. viewport 변경 때문에 picker 선택값이나 폼 draft를 초기화하지 않는다.

후보가 여러 종류면 `전체 · 자금 · 카드 · 투자 · 대출 · 보험` compact 필터와 실제 후보 수를 먼저 보여 주고, 모바일에서는 필터를 줄바꿈하지 않는 내부 가로 목록으로 유지해 자산 목록 높이를 침범하지 않는다. trigger는 종류 아이콘·이름·종류·소유자를 48px 안팎의 한 덩어리로 압축하고, 각 option은 이름·금액을 첫 줄, 종류·소유자를 둘째 줄에 둔 52~56px 구분선 행으로 보여 준다. 신용카드는 잔액 대신 가장 가까운 미결제 결제 예정액을 표시한다. 320px에서는 한 열, 충분한 폭에서는 두 열로만 밀도를 높이며 항목 하나를 큰 카드로 만들지 않는다. 이체와 자동이체·결제 계좌의 서버 후보 제한은 그대로 유지하고, 보관 자산은 새 선택 후보에서 제외하되 과거 거래가 참조하는 현재 선택은 `현재 목록에 없음`으로 식별 가능하게 남긴다.

trigger의 접근 가능한 이름은 안정적인 field label로 유지하고 현재 선택 상세는 설명으로 연결한다. picker는 접근 가능한 title·description, 최소 44px 조작 목표, `aria-pressed`, Escape·바깥 영역 닫기, 닫힌 뒤 trigger focus 복구, 페이지 전체 가로 overflow 없음 계약을 지킨다. 후보 수가 최대 50개이므로 검색 입력은 당장 추가하지 않고 종류 필터로 탐색 비용을 줄이며, 실제 사용에서 이름 검색 필요가 확인되면 동일 overlay 안에 Combobox 검색을 확장한다.

picker를 열 때마다 로그인한 현재 구성원이 개인 소유자로 표시된 자산만 기본 노출하고, 헤더 우상단의 `모든 자산 보기` switch를 켜면 해당 field의 전체 후보인 다른 구성원 자산까지 보여 준다. 이 필터는 실수 방지를 위한 초기 탐색 범위일 뿐 권한이나 서버 후보 계약을 바꾸지 않는다. switch를 바꾸면 종류 필터만 `전체`로 되돌리고 폼 draft와 현재 선택은 유지하며, picker를 닫았다가 다시 열면 내 자산 보기로 돌아간다. 편집 중 현재 선택이 다른 구성원 자산이어도 값을 바꾸지 않고 목록에서 확인할 수 있는 진입점을 제공한다. 신용카드 금액 보조 정보는 달력상의 이번 달 값에 고정하지 않고, 이번 달 미결제 결제 예정액이 있으면 이를, 없으면 다음 달의 가장 가까운 결제 예정액을 `결제 예정`으로 표시한다.

현재 로그인 구성원이 경제활동 주체인 지출 저장이 성공하면 그 결제 자산 ID를 현재 가계부·구성원 범위의 브라우저 선호값으로 기억하고, 다음 일반 지출 작성에서 해당 자산이 여전히 활성 후보일 때 기본 선택한다. 다른 구성원의 지출을 대신 기록하거나 수입·이체를 저장하는 경우에는 이 값을 덮어쓰지 않는다. 날짜 상세에서 전달된 초안이나 자산 원장에서 여는 빠른 기록처럼 화면 문맥이 자산을 명시하면 그 문맥을 우선하며, 자산이 보관·삭제되었거나 다른 가계부·구성원의 값이면 기존 빈 기본값으로 안전하게 돌아간다. 브라우저에는 자산 ID 외의 이름·금액·금융 데이터를 저장하지 않고 저장소 접근 실패가 거래 저장을 실패시키지 않게 한다.

### D-051 자산 원장과 거래 상세 우선 탐색

자산 현황의 자산 행은 설정 form이 아니라 `/assets/{assetId}`의 자산 원장으로 이동한다. 활성 자산만 `자산 편집`을 제공하고 사용 종료 자산은 과거 원장과 잔액을 읽으며 `다시 사용`할 수 있다. 종료 기능의 화면 용어는 `자산 삭제 또는 사용 종료`·`처리 방법 확인`을 사용한다.

`GET /api/assets/{assetId}/transactions`는 기간 전체를 한 번에 읽지 않고 날짜·생성 시각·ID 내림차순 cursor로 30건씩 조회한다. 해당 자산이 `primary_asset_id`인 거래와 해당 자산 posting이 있는 거래를 합쳐 거래당 한 번만 반환하므로, 체크카드처럼 선택 자산과 실제 차감 계좌가 다른 거래는 양쪽 자산에서 맥락에 맞게 찾을 수 있고 이체도 보내는·받는 자산 양쪽에서 찾을 수 있다. 모바일은 최신 거래부터 한 열로 이어서 스크롤하고 페이지 끝 근처에서 다음 cursor를 불러오며, 펼쳐진 전체 결과를 날짜 구분자 하나씩으로 묶는다(D-073). iPad·데스크톱도 같은 조회·정렬·일별 묶음을 유지한다.

자산 원장은 자산 현황으로 돌아가는 동선을 모바일 context header와 iPad·데스크톱 본문 상단에 항상 제공한다. 각 거래 행 오른쪽에는 해당 거래 금액과 함께 그 거래까지 반영한 `잔액`을 표시한다. 잔액은 서버의 현재 잔액에서 실제 해당 자산 posting을 최신순으로 역산하며, 체크카드처럼 선택 자산과 실제 posting 자산이 다르면 선택 자산의 잔액을 임의로 움직이지 않는다. `잔액 기준일` 시작 시점에는 실제 거래가 아닌 `기준일 잔액` 행을 날짜 순서에 삽입하고 사용자가 입력한 기준일 잔액을 표시한다. 기준일 이전 거래도 이 기준점에서 역산한 거래 후 잔액으로 이어 보이지만 현재 잔액 계산에는 다시 합산하지 않는다. 기준일 행은 cursor가 해당 날짜를 지나거나 마지막 page를 읽은 뒤에만 한 번 표시한다.

거래 행은 곧바로 편집하지 않고 `/transactions/{transactionId}` 상세를 먼저 연다. 상세에는 날짜·금액·분류·자산 흐름·경제활동 주체·집계 포함 여부·내용을 표시하고 일반 거래만 하단에 `기록 편집`과 `기록 삭제`를 둔다. 편집은 `/transactions/{transactionId}/edit`로 분리하고, 삭제는 상세에서 최신 version을 보내 `412`이면 최신 상세를 다시 읽은 뒤 재확인을 요구한다. 카드 구매는 기존 정정·환불 전용 상세로, 카드 환불과 자동 정산 같은 시스템 거래는 정확한 거래 상세를 읽되 일반 편집·삭제를 노출하지 않는다. 생성·수정·삭제 뒤 자산 원장·홈·통계·자산·카드 명세 query를 stale 처리해 다시 진입할 때 같은 서버 상태를 보여 준다.

활성 자산 원장에는 `기록 추가`를 두고 현재 route를 유지한 채 반응형 거래 기록 dialog를 연다. 원장의 자산은 지출·수입의 자산과 이체의 보내는 자산 초깃값으로 채우되 사용자가 다른 자산이나 거래 종류를 선택할 수 있다. 저장하면 dialog만 닫고 자산 상세·원장·홈·통계·카드 명세 query를 다시 조회해 현재 잔액과 최신 행을 즉시 맞춘다. 작성 중 닫기·바깥 영역·Escape는 초안 폐기 확인을 거치며 `계속 작성`을 선택하면 입력을 그대로 유지한다. 보관 자산에는 신규 기록 행동을 노출하지 않는다.

### D-052 홈 제목과 거래 초안 이탈 보호

홈은 모바일·태블릿·데스크톱 모두 달력과 월간 요약이 곧 화면의 문맥이므로 시각적인 `가계부` 대제목 header를 두지 않는다. 문서 구조와 보조 기술 탐색을 위한 숨은 `h1`만 유지한다.

거래 생성·수정 form에는 별도 `취소` 버튼을 두지 않는다. 사용자가 실제로 초안을 바꾼 뒤 하단·사이드 메뉴, 편집 화면의 뒤로가기 또는 브라우저 history로 다른 화면을 열려고 할 때만 `입력한 내용은 저장되지 않고 모두 사라져요.`라고 알리고 `계속 작성`과 `나가기`를 선택하게 한다. 새로고침·탭 닫기처럼 앱 dialog를 표시할 수 없는 브라우저 이탈에는 표준 `beforeunload` 경고를 사용한다. 저장·삭제 성공과 초안을 그대로 넘기는 새 거래 전환은 데이터가 사라지지 않으므로 막지 않는다.

### D-053 완료된 카드 결제의 출금 계좌 정정

카드 선결제·자동 정산에서 잘못된 계좌가 출금 출처로 기록되면 카드 명세의 결제 기록에서 `출금 계좌 변경`으로 정정한다. 일반 거래 삭제로 우회하지 않으며 금액·결제일·결제 유형·명세의 결제 완료 금액은 유지하고, 결제 기록의 계좌와 해당 시스템 이체의 음수 posting을 한 데이터베이스 트랜잭션에서 새 계좌로 옮긴다. 자동 정산이면 완료된 schedule의 실행 계좌도 함께 맞춘다. 그 결과 기존 계좌 잔액은 복원되고 새 계좌 잔액은 같은 금액만큼 감소하며 카드 잔액과 수입·지출 통계는 변하지 않는다.

정정 계좌는 같은 가계부의 활성 `payment_source_capable` 자산만 허용하고 명세 version을 이용해 동시 수정을 `412`로 거부한다. 프론트는 최신 명세를 다시 읽되 사용자가 고른 계좌는 보존해 재확인할 수 있게 한다. 이미 카드 구매 환불 금액이 해당 결제 계좌로 반환된 결제는 반환 posting까지 함께 옮겨야 하므로 MVP 전용 정정 대상에서 제외하고 `409`로 안내한다.

### D-054 계좌·적금의 금융기관 식별

`BANK` 계좌와 `SAVINGS` 적금은 고정 금융기관 카탈로그 코드를 선택해 저장한다. 새 클라이언트는 등록·수정 시 금융기관 선택기를 제공하고, 필드를 보내지 않는 이전 PWA와 기존 데이터는 `OTHER`로 정규화해 저장·이관한다. 다른 자산 종류의 금융기관 코드는 `null`로 정규화한다.

자산 현황과 자산 선택기·원장·편집 목록에서는 계좌·적금에 작은 원형 금융기관 아이콘과 기관명을 함께 표시한다. 공식 소형 로고를 확인한 기관은 공식 웹 리소스를 쓰고 외부 이미지가 실패하거나 확인되지 않은 기관은 같은 크기의 색상·약칭 fallback을 즉시 보여 준다. 자산 현황의 자금 그룹은 현금성 자산을 먼저 두고 계좌·적금을 금융기관 카탈로그 순서로 인접 정렬한 뒤 자산 종류·이름 순으로 정렬한다. 기관은 표시·탐색 정보이며 소유권·거래 권한·posting 계산에는 영향을 주지 않는다.

### D-055 신용·체크카드의 카드사 식별

`CREDIT_CARD`와 `DEBIT_CARD`는 금융기관과 분리된 고정 카드사 카탈로그 코드를 선택해 저장한다. 기존 카드와 필드를 보내지 않는 이전 PWA는 `OTHER`로 정규화하고, 카드가 아닌 자산에서는 카드사 코드를 `null`로 정규화한다. 카탈로그와 확인된 브랜드 이미지는 프론트 번들에 정적으로 포함하며 실행 중 외부 카드사나 CDN에 요청하지 않는다.

등록·수정 화면은 카드 종류를 선택했을 때만 카드사 선택기를 보여 준다. 자산 현황·거래 자산 선택기·자산 원장·데스크톱 편집 목록에는 동일한 원형 카드사 표식과 이름을 보여 주고, 별도 공식 소형 이미지가 없는 카드사는 브랜드 색상·약칭 fallback으로 같은 정보 밀도를 유지한다. 카드사 코드는 표시·탐색 정보이고 정산·결제 계좌·posting 계산에는 영향을 주지 않는다.

### D-056 사용 종료 자산 다시 사용과 카드 결제 취소

내부 archive 상태는 거래가 연결된 자산의 과거 식별자·posting·잔액 흐름을 보존하기 위한 구현 세부로 두고, 사용자에게는 `사용 종료`로만 표현한다. 사용 종료 상세에서 `다시 사용`할 수 있으며 기존 거래·잔액을 변경하지 않고 활성 자산 50개 제한과 연결 계좌 유효성을 다시 검증한다. 신용카드는 다시 사용해도 자동 정산 schedule을 재생성하지 않는다(D-069).

사용자가 직접 실행한 카드 선결제와 시스템 자동 정산은 명세 상세의 결제 기록과 거래 상세 양쪽에서 같은 취소 command로 취소할 수 있다. 거래 상세 응답은 연결된 명세·결제 식별자와 명세 version을 제공해 일반 거래 삭제로 우회하지 않고 같은 동시성·원장 계약을 사용한다. 취소는 결제 행과 원 거래를 감사 이력으로 남기되 연결 거래를 soft delete하여 결제 계좌·카드 잔액과 명세 잔액·상태를 한 트랜잭션에서 복원한다. 모든 결제 취소는 자동 정산 일정을 다시 열지 않고 과거 schedule을 `CANCELLED`로 유지한다(D-069). 환불 반환이 연결된 결제와 이후 정규 결제가 연결된 선결제는 단순 취소하지 않고 충돌로 안내한다.

### D-057 대출·투자 금융기관 식별

`LOAN`은 기존 은행·상호금융과 여신금융협회 기준 주요 캐피탈사를, `INVESTMENT`는 금융투자협회 기준 주요 증권사를 고정 정적 카탈로그에서 선택한다. 같은 `financial_institution_code` 저장 슬롯을 사용하되 백엔드는 자산군에 맞지 않는 코드를 거부한다. 기존 대출·투자 자산은 이름으로 기관을 추정하지 않고 `OTHER`로 이관하며 금액·거래·소유자·기준일은 바꾸지 않는다.

등록·수정 선택기는 모바일 drawer·넓은 화면 popover의 고정 높이 안에서 주요 기관과 그 외 기관을 compact 버튼 grid로 보여 준다. 자산 현황·자산 선택기·원장·편집 목록은 계좌·적금과 동일한 원형 로고 또는 브랜드 색상·약칭 fallback과 정확한 기관명을 사용한다. 기관 코드는 탐색용 표시 정보이며 잔액·통계·posting·권한에 영향을 주지 않는다.

### D-058 월간 통계 분류의 거래 내역 탐색

월간 통계의 수입·지출 분류 행은 선택할 수 있으며, 선택하면 해당 월과 해당 분류가 통계 합계에 실제로 기여한 거래 내역을 최신순으로 보여준다. 현재 통계의 거래 주체와 자산 소유자 필터를 동일하게 적용하고 사용자 선택 집계 제외 거래, 이체와 카드 정산은 내역에서도 제외해 분류 순금액과 거래 합이 어긋나지 않게 한다. 지출 환불은 통계 기여액을 양수로 표시해 원 지출을 줄인 효과를 드러낸다.

거래 내역은 전체 원장을 한 번에 읽지 않고 월 반개구간과 분류 ID를 필수로 하는 cursor pagination으로 조회한다. 각 행은 날짜·내용·자산·구성원·signed 통계 기여액을 보여주고 기존 거래 상세로 이동할 수 있다. 모바일은 전체 화면 dialog, iPad·데스크톱은 폭과 높이가 제한된 dialog로 같은 목록 DOM을 사용한다.

### D-059 대표 결제의 실제 결제액과 지출 반영액 분리

사용자 지출은 `대표로 결제했어요`를 선택해 실제 결제액과 달력·통계에 반영할 개인 부담액을 분리할 수 있다. 개인 부담액은 0원 이상 실제 결제액 이하의 정수 원이며, 대표 결제를 사용하지 않거나 이전 클라이언트가 필드를 생략하면 실제 결제액과 같다. 자산 posting, 체크카드 연결 계좌 차감, 신용카드 charge·명세·결제 예정은 항상 실제 결제액을 사용하고 월간 달력·통계·분류별 거래 기여액만 개인 부담액을 사용한다. 집계 제외를 함께 선택하면 두 금액과 자산 원장은 보존하되 달력·통계에는 포함하지 않는다.

일반 지출 수정과 카드 구매 기록 정정에서도 같은 두 금액을 변경할 수 있다. 카드 환불은 실제 환불액으로 카드·결제 계좌 원장을 보정하고, 환불일 지출에서는 사용자가 지정한 차감액만 상쇄한다. 환불 차감액은 실제 환불액과 원 구매에 남은 지출 반영액을 넘을 수 없고, 카드 구매 정정으로 지출 반영액을 이미 환불에서 차감한 누적액보다 작게 만들 수 없다. 거래 상세와 카드 구매 상세·환불 이력은 실제 금액과 다른 경우 지출 반영액을 함께 보여준다.

### D-060 공통 원화 계산기 키패드

모든 공통 `MoneyField`는 포커스할 때 사칙연산을 지원하는 앱 내부 계산기 키패드를 연다. 모바일과 설치형 PWA에서는 시스템 가상 키보드를 요청하지 않는 `inputmode="none"` 입력과 화면 하단의 safe area 대응 키패드를 사용하고, `768px` 이상 태블릿·데스크톱에서는 같은 키패드 DOM을 입력 바로 아래 popover로 재배치한다. 일반 키보드 입력과 붙여넣기도 계속 허용하며 닫기·viewport 변경으로 폼 draft를 잃지 않는다.

계산은 정수 원 단위만 지원한다. 0으로 나누기, 원 단위로 나누어떨어지지 않는 나눗셈, 안전한 정수 범위 초과와 필드가 허용하지 않는 음수 결과는 실제 폼 금액을 바꾸지 않고 인라인으로 설명한다. 두 번째 피연산자는 `=` 또는 다음 연산자로 계산이 확정될 때만 폼 draft에 반영한다.

계산기 버튼은 Vibration API를 제공하는 기기에서 사용자 상호작용마다 10ms의 짧은 촉각 피드백을 요청한다. 브라우저·OS·사용자 설정이 진동을 차단하거나 API를 제공하지 않으면 오류·권한 요청·대체 효과 없이 건너뛴다. 웹은 시스템 키보드의 햅틱 설정값을 읽을 수 없고 WebKit은 해당 API를 지원하지 않으므로 iPhone·iPad에서는 무진동이 정상 동작이다.

### D-061 금융자산 공동 소유 제거

2026-10-07 사용자 결정으로 모든 자산의 명의자는 같은 가계부 구성원 한 명으로 한정한다. 공동 소유 선택·표시·필터를 제거하고 자산 수정에는 구성원 소유자 선택만 둔다. 새 자산의 기본 소유자는 현재 구성원이다. 소유자는 계속 권한과 무관하며 다른 구성원의 자산 사용·수정과 교차 소유 정산을 허용한다. 카드 정산의 거래 주체·posting·통계 정책은 바꾸지 않는다.

API와 DB의 `ownershipScope`는 기존 개인 자산 클라이언트와의 호환을 위해 `PERSONAL`만 허용하고 `ownerMemberId`를 필수로 한다. 통계 소유자 필터는 `ALL|MEMBER`만 받는다. 이전 `owner=joint` URL은 자산에서는 현재 구성원, 통계에서는 전체 소유자라는 기본 범위로 해석한다. 저장 후 query 무효화와 다른 세션의 재조회 경계는 기존 계약을 유지한다.

기존 데이터의 명의자는 임의로 지정하지 않는다. V29는 사용 종료 자산을 포함해 공동 소유가 남아 있으면 중단하며, 명의자를 확인해 이전 버전에서 수정한 후 다시 적용한다. 한 가계부에서 공동 소유가 없다는 확인을 전체 서비스의 부재로 간주하지 않는다.

### D-062 카드 결제의 명의자 귀속과 기록 조회

카드 자동 정산과 선결제는 결제 생성 시점의 카드 소유자를 `performed_by_member_id`로 기록한다. 결제 계좌 소유자와 실행자는 이 주체와 독립적이다. 자동 정산의 작성자는 계속 null, 수동 선결제의 작성자는 실행한 구성원이다. 이후 카드 소유자 변경이나 출금 계좌 정정은 이미 저장된 결제 주체를 바꾸지 않는다.

V30은 기존 정산·선결제(취소 이력 포함)를 연결된 명세의 현재 카드 소유자로 채운다. 과거 명의자 snapshot이 없으므로 이 기준을 사용하며 금액·날짜·posting·작성자는 보존한다. 명세·결제 연결이 없어 주체를 채울 수 없는 기록은 제약 검증에서 실패한다.

월간 달력은 기존 수입·지출 합계와 별도로 날짜별 `cardPaymentWon`을 반환해 카드결제 금액을 표시한다. 카드 명의자의 구성원 필터와 모두 보기에서 날짜 상세·일별 목록·거래 상세로 이어진다. 결제 취소 기록은 조회에서 제외한다. 모든 수입·지출·순액·통계에는 계속 포함하지 않는다. 기존 query 무효화·진입·focus 재조회 계약을 사용하고 별도 cache는 만들지 않는다.

### D-063 실제 운영 식별정보의 비공개 관리

공개 저장소에는 구성 원칙, 환경변수 이름과 가상 예시만 기록한다. 실제 내부 IP·관리 포트 조합, DB 이름·계정, 서버 사용자명·절대 경로, 운영 도메인과 private 배포 저장소·runner 식별자는 비공개 운영 문서 또는 호스트 설정으로 분리한다. 테스트 fixture에도 실제 운영값을 재사용하지 않는다. 이 원칙은 비밀번호·토큰의 기존 secret 관리 규칙에 더해 적용한다. 코드의 안전한 기본값과 표준 프로토콜·포트는 공개할 수 있으나 실제 운영에서 사용하는 값으로 명시하지 않는다. 과거 Git 이력과 외부 사본은 현재 문서 수정만으로 제거되지 않으며, 원격 반영과 이력 재작성은 각각 별도로 승인받는다.

### D-064 카드 미결제 섹션과 수동 전액 결제

카드 자산 상세의 거래 내역 위에 `미결제 내역`을 명세별 별도 섹션으로 제공한다. 남은 금액이 있는 명세를 cursor로 조회하고 결제 예정일·남은 금액·명세 보기·결제하기를 표시한다. 이는 화면 구분이며 수입·지출 분류를 새로 만들지 않는다.

자동 정산 사용 여부와 결제일 경과에 관계없이 활성 카드의 OPEN/FINALIZED 명세를 수동으로 전액 결제할 수 있다. 기존 결제일 전 부분·복수 선결제는 유지한다. `POST /api/card-statements/{statementId}/payments`는 확인한 명세 version·남은 금액·결제 계좌와 idempotency key를 받아 현재 값이 다르면 412로 전체 거부한다. 기존 상세 조회를 확인에 사용하며 별도 preview API는 추가하지 않는다. 결제일은 사용자가 입력한 실제 출금일이며(D-066), 주체는 현재 카드 소유자, 작성자는 실행자다. 실제 은행 요청 없이 장부에 계좌→카드 이체를 기록한다.

V31은 결제 유형 MANUAL을 추가한다. 수동 전액 결제는 TRANSFER/CARD_SETTLEMENT, source_type=SYSTEM이며 작성자를 필수로 둔다. 잔액 부족에도 음수를 허용하고 수입·지출 통계에서 제외한다. 명세를 PAID로 만들고 유효 자동 예약을 완료 처리해 중복 출금을 막는다. worker와 수동 명령은 명세→schedule 순서로 잠근다. 수동 전액 결제 취소는 잔액·미결제를 복원하되 자동 예약을 취소 상태로 유지해 즉시 재정산하지 않는다. 출금 계좌 정정과 환불 반환은 기존 결제 원장을 재사용한다.

저장 후 명세·자산·원장 query를 무효화하고 다른 세션은 진입·focus·수동 새로고침으로 다시 읽는다. 확인 중 변경된 금액·계좌는 자동 승인하지 않으며 최신 내용 확인 후 다시 누르게 한다. 오프라인·처리 중에는 결제 버튼을 막고 실패한 요청의 같은 idempotency key를 보존한다.

### D-065 결제 완료 후 뒤늦게 추가된 카드 사용

결제일 당일 또는 이후에 이미 전액 결제한 명세에 청구 대상 사용 내역이 추가되거나 증액되면 기존 결제를 유지하고 차액만 미결제로 다시 연다. 이 명세에는 추가 사용 표시를 보존하고 자동 정산을 다시 실행하지 않는다. 자동 정산 설정 변경도 이 제한을 해제하지 않으며 사용자가 미결제 결제 버튼으로 남은 전액을 별도 기록한다. 자산 미결제 섹션과 명세 상세에는 `결제 후 사용 내역이 추가됐어요`와 직접 결제 안내를 표시한다. 결제일 전 전액 선결제 뒤 추가 사용도 자동 예약을 만들지 않는다(D-069). 완료 판정은 실제 남은 금액 0원만 허용한다.

### D-066 수동 카드 결제의 실제 출금일

수동 전액 결제 dialog에서 `결제일`을 입력받아 해당 날짜에 결제 계좌에서 출금된 것으로 기록한다. 기본값은 서울 기준 오늘이고 과거 날짜를 선택할 수 있다. `paidOn`은 결제 이력과 연결 이체의 경제활동일에 동일하게 적용하며 달력·자산 원장도 그 날짜를 기준으로 조회한다. 작성 시각은 실제 요청 시각으로 유지하고 기준일 이전 posting의 잔액 계산은 기존 D-004를 따른다.

이전 PWA가 날짜를 생략하면 기존처럼 서울 실행일을 사용한다. 요청 키에 날짜를 포함해 다른 날짜로 재사용하면 거부하고, 같은 요청 재시도는 최초 저장 날짜를 유지한다. 처리 중·결과 불명확한 재시도에서는 날짜를 고정하며 충돌 후 최신 내용 확인과 화면 회전에도 선택 날짜를 보존한다. 자동 정산과 부분 선결제의 날짜 정책은 유지한다. 기존 결제일을 소급 변경하거나 DB migration을 추가하지 않는다.

### D-067 ARM64 검증 이미지 재사용과 CI 검사 분리

2026-10-07 사용자 승인으로 M4 Mac mini 운영 플랫폼을 `linux/arm64`로 고정한다. PR은 기존 Q-030의 핵심 Chromium E2E와 변경 영향 시나리오를 실행하고, main은 전체 E2E를 실행한다. build·unit·DB·API 계약 검사는 양쪽에서 유지한다. 공개 GitHub-hosted ARM64 환경에서 검증한 JAR·dist를 runtime image에 한 번 포장하고 같은 image artifact를 모든 E2E shard가 사용한다. 성공한 main push run만 해당 이미지를 게시하고 SHA·run ID/attempt·digest를 묶은 release manifest를 만든다. 운영은 성공한 최신 main과 manifest를 대조하고 digest를 pull하며 다시 build하지 않는다. 백업·격리 복원·readiness·외부 smoke와 기존 예약/즉시 배포 승인 경계는 유지한다.

초기 병렬 후보는 독립 환경 2개 × 워커 2개다. 워커 1/2/3 각각 3회, retry 없는 비교를 통해 소요 시간·메모리·swap·실패를 측정한 뒤 조정하며 측정 전에는 최적값 또는 실제 단축 시간을 확정하지 않는다. 세부 계약과 원격 활성화 조건은 [`operations/ci-release-pipeline.md`](operations/ci-release-pipeline.md)를 따른다.

### D-068 이체 목적과 적금·투자 통계

2026-10-07 사용자 승인으로 일반 이체에 `GENERAL`, `SAVINGS_DEPOSIT`, `INVESTMENT_DEPOSIT`, `SAVINGS_WITHDRAWAL`, `INVESTMENT_WITHDRAWAL` 목적을 저장한다. 기존 이체와 목적 없는 신규 요청은 일반 이체이고, 목적 없는 수정 요청은 기존 목적을 보존한다. 자산 종류는 기본 제안에만 사용하고 과거 목적을 재분류하지 않는다. 계좌→적금/투자는 납입, 적금/투자→계좌는 인출을 제안하며 적금·투자 간 재배치는 일반 이체가 기본이다. 목적은 사용자가 직접 선택할 수 있는 통계 메타데이터이며 기존 허용 자산 경계 안에서 별도 자산 종류 제약을 추가하지 않는다.

원장 posting과 잔액 기준일 계약을 유지하고 별도 지출 거래를 생성하지 않는다. 기존 수입·소비 지출·순액과 홈 달력은 유지하고 통계에 소비+적금 납입+투자 납입인 총 사용액을 추가한다. 회수는 수입이나 과거 납입 취소로 보지 않고 회수일에 집계하며 순납입=납입−회수다. 총 사용액은 회수액을 차감하지 않는 배분 지표이고 수입−총 사용액은 현재 잔액이나 순자산 증가가 아니다. 이자·투자 손익은 별도 기록하며 자동 계산하지 않는다. 카드 정산·선결제·기준일 잔액은 적금·투자 통계에도 제외한다.

통계는 D-070의 통합 화면으로 제공하고 월·구성원·자산 소유자·분류 필터를 URL에 보존한다. 월간·연간의 납입·회수는 거래 주체 기준이며 소유자 세부 필터는 납입의 도착 자산, 인출의 출발 자산 현재 소유자를 사용한다. 수입·지출 분류 필터를 지정하면 분류 없는 이체는 제외한다. 기존 분류는 수입·지출용으로 유지한다. 이 결정은 D-009/D-038/D-041/D-047의 이체 전체 통계 제외 정책을 위 범위에서 대체한다.

### D-069 자동 카드 정산 제거와 내역 선택 결제

2026-10-07 사용자 결정으로 카드 자동 결제를 제거한다. 신규 자동 예약·worker 실행을 중단하고 미처리 예약만 취소하며 과거 결제·posting은 보존한다. 구버전 API의 자동 정산 필드는 호환을 위해 false로 정규화한다. 카드 등록의 정산일·결제 월/일·기본 결제 계좌는 유지하되 실제 결제마다 출금 계좌와 실제 결제일을 선택한다.

2026-10-09 사용자 결정으로 신용카드 자산 상세의 카드 대금 요약 머리에 `대금 결제` 링크를 두고, `/assets/:assetId/card-payment` 별도 페이지에서 `내역 선택 결제`·`부분 금액 결제` 탭을 제공한다. 결제 페이지에서 해당 카드 자산으로 돌아갈 수 있고 직접 진입·새로고침을 지원한다. 기본 체크는 서울 기준 오늘 이하의 가장 최근 정산일(29~31일이 없는 달은 말일)까지 마감된 명세의 미결제 항목이다. 정산 당일은 해당 날짜를 포함한다. 결제일 전후로 범위를 바꾸지 않는다. 10/12와 10/30 모두 말일 정산 카드라면 9/30까지의 미결제 항목이 기본 선택된다. 미래 명세의 할부 회차는 기본 선택하지 않으며 회차별로 직접 골라 미리 결제할 수 있다. 기준일 부채는 별도 한 항목으로 표시하고 기준일 이전 구매를 다시 청구하지 않는다.

부분 금액 탭은 카드 전체 미결제액 내에서 입력하며 결제 예정일·사용일·항목 ID 순서로 배분한다. 날짜에 따른 부분 결제 제한은 제거한다. 두 탭은 선택·금액·계좌·날짜 draft를 공유 또는 보존하고 화면 회전·focus 재조회로 초기화하지 않는다. 목록은 cursor로 읽고 기본 선택 합계는 아직 불러오지 않은 대상도 포함한다. 선택 조건과 제외/추가 ID, 서버 snapshot을 한 command로 제출해 전체를 원자적으로 기록한다.

구매일 지출·명의자 귀속·통계 제외·음수 계좌 허용·기록 정정/환불의 명세 내 미결제 우선 및 초과분 실제 계좌 반환 정책은 유지한다. 선택 결제의 항목별 배분을 저장하되 기존 명세 단위 결제액과 정정/환불 후 남는 명세 결제액은 오래된 항목부터 반영한다. 이는 과거 계좌·금액·날짜를 변경하지 않는다. 취소는 결제 배분을 함께 해제한다. D-008/D-030/D-037/D-056/D-064~066의 자동 실행 및 부분 결제 시점 제한을 이 결정으로 대체한다.

### D-070 통합 사용처 순위와 가로 막대 비교

2026-10-08 사용자는 생활 지출뿐 아니라 저축·투자에 쓴 금액도 같은 소비 관점으로 비교하는 사용처 순위를 승인했다. 통계 첫 화면은 수입·지출·총계 요약 → 통합 사용처 순위 → 월별 흐름 순서다. 2026-10-09 사용자 결정으로 상단은 수입(기존 초록) → 지출(기존 붉은색) → 총계(기본 검정) 순서이며, 어두운 화면에서는 총계의 기본 밝은 글자로 대비를 유지한다. 지출은 생활 지출과 적금·투자 납입의 총 사용액을 자금 감소 부호로 표시하고 총계는 수입−총 사용액이다. 식비·주거비 등 각 지출 분류와 적금 납입·투자 납입을 한 목록에서 금액 내림차순으로 정렬하며, 생활 지출을 `소비` 한 항목으로 먼저 묶지 않는다. 순위·이름·원 단위 금액·총 사용액 대비 비중·동일 척도 가로 막대를 각 행에 함께 표시한다. 상위 6개와 전체 펼치기를 제공하며 원형 차트나 기타 조각으로 합치지 않는다. 납입·회수·순납입은 월별 흐름 아래의 접힌 보조 영역에 둔다. 수입 분류 조회와 지출 분류별 거래 탐색은 유지한다.

총 사용액은 환불을 반영한 지출 순금액+적금 납입+투자 납입이며 회수액을 차감하지 않는다. 순위에서도 사용액은 양수, 순환불은 음수로 표시한다. 전체 합계 또는 포함된 분류 순금액이 0 이하이면 비율·막대를 숨기고 순금액과 환불 안내를 유지한다. 납입이 0원인 적금·투자는 순위에 추가하지 않는다. 같은 이름의 지출 분류와 납입은 별도 행으로 유지하며 납입 표기로 구분한다.

DB·API·posting·구성원/소유자/분류 필터 계약은 바꾸지 않는다. 저축·투자는 내부적으로 이체로 유지하고 일반 계좌 이체와 카드대금 결제는 사용액에 중복 반영하지 않는다. 기존 `view=consumption|formation` 링크는 다른 필터를 보존한 채 통합 화면으로 정규화한다. 신규 차트 라이브러리는 추가하지 않는다.

### D-071 마지막 신규 거래의 날짜 기본값

2026-10-09 사용자 요청으로 일반 거래 입력과 자산 원장의 빠른 기록은 현재 로그인한 입력자가 마지막으로 신규 저장에 성공한 거래의 경제활동일을 기본 선택한다. 수입·지출·이체·신용카드 구매에 공통 적용하며 날짜의 최댓값이 아니라 저장 성공 순서를 따른다. 다른 구성원의 거래를 대신 입력해도 입력자의 선호값만 바꾼다. 기존 거래 수정·정정·삭제, 환불·카드대금 결제와 실패·취소한 입력은 이 값을 바꾸지 않는다.

명시적으로 선택한 달력 날짜와 전달받은 초안, 기존 거래 편집 값은 기억한 날짜보다 우선한다. 기본값은 폼 최초 초기화에만 읽고 focus 재조회·탭 간 저장·회전으로 이미 작성 중인 날짜를 바꾸지 않는다. 캐시가 없거나 잘못되었으면 서울 기준 오늘을 사용한다.

구현은 가계부 ID·현재 구성원 ID별 versioned localStorage key에 `YYYY-MM-DD` 한 값만 저장하는 입력 선호값이다. API 응답·금액·거래 목록은 영속 캐시하지 않고 DB/API 조회를 추가하지 않는다. 별도 key로 다른 범위의 동시 저장을 분리하고 저장소 접근·쓰기 실패는 입력·저장 완료를 막지 않는다. 만료 기한 없이 다음 신규 저장으로 갱신하며 로그아웃·재로그인에도 같은 범위에서 재사용한다. 새 기기·별도 브라우저/PWA 저장 공간·사이트 데이터 삭제 시에는 오늘로 시작하고 과거 DB 이력을 조회해 복원하지 않는다. 웹과 설치형 PWA의 같은 구현을 사용하되 기기 간 또는 분리된 저장 공간 간 동기화는 제공하지 않는다.

### D-072 메인 달력의 날짜별 금액과 건수

2026-10-09 사용자 요청으로 메인 월간 달력의 날짜 칸을 옅은 가로·세로 그리드로 구분하고 날짜·금액을 칸 위쪽 왼편에 정렬한다. 사용자의 가독성 피드백에 따라 그리드는 유지하되 옅은 구분선으로 낮추고, 요일과 달력 외곽을 박스로 감싸지 않는다. 이전·다음 달 날짜는 흐리게 표시하며, 월 제목과 작은 날짜 선택 표식으로 읽는 순서를 분명히 한다. 날짜 아래에 작은 수입 빨간색 `+금액`, 지출 파란색 `-금액`을 각각 독립 행으로 놓고 그 아래 합산 거래 `n건`을 표시한다. 메인 달력의 이 색상은 기존 D-026의 녹색 수입·붉은 지출보다 우선하며 다른 화면의 색상 계약은 유지한다. 오늘·선택일은 날짜 숫자 주위 원형 표식으로 구분하고 일요일·토요일도 각각 빨강·파랑으로 식별한다. 모바일·태블릿·데스크톱은 같은 DOM과 날짜 선택·상세·구성원 필터를 사용한다.

건수는 기존 달력 집계 범위와 같은 수입·지출·환불·카드결제를 거래당 한 번 센다. 일반 이체·집계 제외·삭제된 거래·기준일 잔액은 제외하며 금액이 상쇄되어 0원이 되어도 건수는 남긴다. 기존 월간 SQL의 같은 snapshot에서 `transactionCount`를 반환하고 목록 pagination이나 별도 날짜별 요청으로 계산하지 않는다. 신용카드 구매와 대금 결제는 각각 자기 날짜의 한 건이고 결제 금액은 계속 수입·지출과 분리한다. 환불 순액은 지출을 줄이는 파란색 `+금액`이며 수입으로 재분류하지 않는다.

금액은 100만 원 미만이면 천 단위 쉼표를 포함해 표시하고 그 이상은 좁은 셀에서 기존 축약을 사용한다. 정확한 원 단위 금액과 건수는 접근 가능한 날짜 이름·title에서 확인한다. 신규 API 필드는 이전 PWA와 호환되는 추가 필드이며 DB 구조·posting·통계 계산은 바꾸지 않는다.

### D-073 날짜별 공통 거래 목록

2026-10-09 사용자 요청으로 자산 원장도 홈 일별보기와 같이 날짜별로 묶는다. 날짜 제목은 12px normal로 연·월·일·요일을 표시하고 평일은 회색, 토요일은 파란색, 일요일은 빨간색으로 낮은 위계의 구분점 역할을 한다. 현재 불러온 거래 건수를 한 번 표시하며, 모든 cursor page를 합친 뒤 묶어 같은 날짜가 페이지 경계에서 나뉘지 않는다. 기준일 잔액은 해당 날짜의 거래 뒤에 한 번 놓고 거래 건수에서 제외한다. 거래 행에서는 반복 날짜를 생략하되 거래 후 잔액·자산 흐름·집계 제외 표시는 유지한다.

홈 일별보기·자산 원장은 공통 날짜 그룹 컴포넌트를 사용하고, 달력 날짜 상세도 같은 거래 목록·행 컴포넌트를 사용한다. 거래 행마다 구분선을 반복하지 않고 거래 목록 왼쪽 들여쓰기(모바일 12px, 태블릿·데스크톱 16px), 행 위아래 여백으로 구분한다. 홈 일별보기와 자산 원장 모두 날짜별로 옅은 구분선 한 개를 둔다. 홈 일별보기는 날짜 머리글을 해당 section 범위 안에서 CSS sticky로 상단에 유지한다. 다음 날짜가 이전 날짜를 밀어내며 위·아래 스크롤 모두 같은 규칙을 따른다. 머리글은 불투명한 현재 테마 배경과 12px·요일별 색상을 유지하며 복제된 고정 제목이나 scroll listener를 만들지 않는다. 자산 원장의 기존 머리글 배치는 유지한다. DB/API·cursor·query cache 동작은 변경하지 않는다.

### D-074 중립색 라이트·다크 테마

2026-10-09 사용자 요청으로 아이보리 라이트 배경과 녹색 기운의 다크 배경을 제거한다. 라이트는 흰색 `#FFFFFF` 배경·`#FAFAFA` 표면, 다크는 `#121212` 배경·`#1E1E1E` 표면을 사용한다. 본문·보조문·구분선·hover·선택 배경도 중립 회색으로 맞춘다. 페이지·로그인 안내·내비게이션·입력·dialog·popover와 브라우저 theme-color에 공통 토큰을 적용하며, 로고·주요 행동과 수입·지출 의미색은 유지한다. 기존 기기 설정·라이트·다크 선택과 저장 정책은 유지한다.

### D-075 거래 상세의 공통 관리 위치

2026-10-09 사용자 결정으로 수입·지출·이체·카드 구매·카드 결제 기록의 상세는 동일한 폭, 제목, 금액 요약, label/value 행을 사용한다. 관리 행동은 제목 오른쪽의 44px 아이콘으로 제공하고 상세 하단의 별도 관리 영역은 제거한다. 일반 기록의 편집과 카드 구매의 정정은 연필 아이콘, 실제 환불은 환불 아이콘으로 구분하며 접근 가능한 이름과 tooltip을 제공한다. 모바일은 sticky 상단 바 오른쪽에 같은 행동을 제공한다.

일반 기록 삭제는 편집 화면 맨 아래에서만 제공하며 기존 확인·version 충돌 처리를 유지한다. 카드 결제 기록의 취소도 편집 화면 하단으로 이동한다. 카드 구매와 환불에는 기존 정정·환불 및 원 구매 연결만 제공하고 일반 삭제 API를 적용하지 않는다. 서버 계약과 posting·idempotency·cache 무효화는 바꾸지 않는다.

### D-076 자산 상세 행동 배치와 날짜 구분

2026-10-09 사용자 결정: 기록 추가는 자산 설정 옆 44px `+` 아이콘으로 제공하고 거래 목록 위의 큰 버튼은 제거한다. 날짜별 공통 목록은 홈·자산 모두 날짜 머리에 옅은 구분선 하나를 표시하며 거래 행별 구분선은 두지 않는다.

### D-077 자산 거래 검색·필터와 카드 대금 강조

2026-10-09 사용자 결정: 자산 거래 내역 제목은 14px로 줄이고 변경할 수 없는 최신순 문구를 제거한다. 제목 옆 검색·필터 아이콘으로 내용·분류 검색과 기간·거래 종류·구성원 필터를 제공한다. 검색은 서버에서 자산 전체 이력에 적용한 뒤 cursor pagination하며 조건은 URL 및 TanStack Query key에 포함해 복귀와 새로고침에도 유지한다. 필터 결과에는 전체 흐름을 역산한 거래 후 잔액이나 기준일 잔액을 표시하지 않는다. 현재 자산 잔액은 상단에 계속 표시한다. 카드 대금은 가장 가까운 결제일·큰 예정 금액·결제 버튼을 함께 배치하고 다음 결제는 보조 행으로 구분한다.

### D-078 공통 거래 내역과 날짜 스티키

2026-10-09 사용자 결정: 카드·자산 거래 내역과 홈 일별 보기는 검색·필터·로딩·오류·빈 결과·날짜 그룹을 공통 TransactionHistory 컴포넌트로 사용한다. 날짜 머리는 기본 sticky이며 다음 날짜가 양방향 스크롤에서 밀어내고, 모바일 자산 상단 바 높이와 safe area 아래에 붙는다. 자산별 금액·잔액과 홈의 거래 표시는 행 render로만 구분한다.

홈은 선택 월·현재 구성원이 기본이며 검색어·종류·별도 날짜 조건이 있으면 해당 조건으로 전체 이력을 조회한다. 별도 날짜를 생략한 검색은 전체 기간이다. 조회 조건은 URL로 유지하며 월 이동은 검색어·종류·별도 기간을 해제해 선택 월로 돌아간다. 상단 구성원 선택은 월간 달력·일별 보기에서 같은 위치에 항상 표시한다. 구성원 필터는 상단 선택·공통 인라인 필터 도구·월간 달력·요약에서 동일한 URL 상태를 사용하며 보기 전환 시 유지한다. 기존 월간 합계는 선택 월의 요약으로 유지한다. 두 목록 API는 같은 서버 검색 구현을 사용하며 기간 길이 제한 대신 cursor 및 최대 100건 페이지로 조회량을 제한한다.

### D-079 인라인 거래 필터

2026-10-09 사용자 결정: 적용된 검색·필터 요약과 개수 배지는 표시하지 않는다. 필터 아이콘은 제목 아래 한 줄 도구를 펼치고 접는다. 종류·기간·구성원·초기화를 한 줄의 compact 도구로 두고 모바일에서도 가로 스크롤 없이 사용한다. 종류·구성원은 선택 즉시 반영하며 기간은 trigger에 붙는 작은 비모달 popover의 달력에서 시작일·종료일을 선택해 적용한다. 월 제목을 누르면 표시 중인 달 전체를 선택하며, 구성원 도구는 남은 폭을 채우지 않고 내용 너비만 사용한다. 도구는 선택 후에도 열려 있고 다시 아이콘을 눌러 접는다. 홈 상단 구성원 선택과 상태를 공유한다.

### D-080 공통 입력과 필터의 밀도

2026-10-09 사용자 요청으로 Input·NativeSelect·Textarea·날짜·금액 입력의 표면 스타일을 공통화한다. 일반 입력은 데스크톱 40px·14px 글자, 터치 환경 44px·16px 글자를 사용하고 라벨은 13px medium으로 낮춘다. 금액은 48px 높이에 20px 글자로 구분한다. 입력 전용 중립색 테두리와 얇은 focus ring으로 무게를 줄이고 라이트·다크에 함께 적용한다. 필터는 시각적으로 32px인 compact 선택 도구에 44px 조작 영역을 유지한다.

### D-081 운영 인증 메일 발신 도메인

2026-10-09 사용자 결정으로 구매한 도메인의 발신 주소와 Resend SMTP를 사용한다. Cloudflare에서 Resend 발송 도메인을 인증하고 운영 호스트의 비공개 환경파일에 SMTP host·발신 주소·전용 API key를 설정한다. 기존 SMTP gateway를 유지하고 로컬·E2E는 Mailpit을 사용한다. 실제 식별정보와 키는 공개 저장소에 넣지 않으며 backend 재생성 후 실제 수신·링크를 별도로 검증한다.

### D-082 인증 메일의 브랜드 디자인

2026-10-09 사용자 요청으로 인증 메일을 긴 URL 중심의 일반 텍스트에서 돈독 워드마크·짧은 안내·브랜드 초록색 행동 버튼 중심의 HTML로 바꾼다. 발신자 표시 이름은 `돈독`이며 비밀번호 재설정도 같은 템플릿을 사용한다. 인증 24시간·재설정 30분의 기존 일회성 링크 정책을 유지하고 요청하지 않은 수신자를 위한 안내와 대체 링크를 제공한다. UTF-8 HTML과 일반 텍스트를 함께 보내며 로고는 외부 요청 없는 CID PNG로 포함한다. 사용자 이름과 URL은 HTML escape하고 운영 주소는 기존 public URL 설정에서만 가져온다.

### D-083 설정 탐색 구조와 회원 탈퇴

2026-10-09 사용자 승인으로 설정은 B안(공동 가계부·화면·내 계정)의 항목별 탐색으로 구성한다. 데스크톱은 왼쪽 메뉴, 모바일은 상단 메뉴를 사용하고 URL로 선택을 보존한다. 설정에 한해 D-027의 반복 구분선 대신 중립 배경·여백·둥근 섹션 표면을 사용한다. 초대 내역은 펼쳐 보며 가계부 삭제와 계정 탈퇴는 각 목적 영역으로 분리한다. 가계부가 없는 사용자도 계정 설정과 탈퇴에 접근한다.

회원 탈퇴는 기존 개인 나가기 금지의 예외이며 계정을 유지한 채 가계부만 나가는 기능은 추가하지 않는다. 비밀번호 재확인과 처리 내용 동의 뒤 다른 미탈퇴 구성원이 있으면 공동 자산·거래·posting·명의 marker를 보존하고 표시명을 ‘탈퇴한 회원’으로 익명 처리한다. 탈퇴한 member 식별자는 과거 기록·통계 참조로 남으며 접근 권한을 주지 않는다. 마지막 미탈퇴 구성원이면 가계부 전체를 cascade 삭제한다. 이메일은 고유한 익명 값으로 바꾸고 credential·OAuth 연결·인증/reset token·모든 세션과 본인이 발급한 미사용 초대를 폐기한다. 사용자 작성 메모와 자산 이름은 공동 기록에 남는다. 삭제 전 백업은 기존 30일 정책을 따른다.
