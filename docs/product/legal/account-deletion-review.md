# 탈퇴자의 데이터 전체 삭제 영향 검토

> D-087 후속 결정: 이 문서는 초기 검토 기록이다. 실제 구현은 계정 삭제·가계부별 시스템 구성원·개인 관련 텍스트 정리·금액 기록 보존으로 변경되었다. 현재 문서 원본은 [backend legal](../../../backend/src/main/resources/legal/2026-10-09/)이고, [가입 동의 구현 계약](consent-draft.md)을 따른다. 완전한 익명화나 스토어 승인을 보장하지 않는다.


2026-10-09 사용자 요청: 탈퇴자 데이터를 전부 지우는 방향에서 문제가 될 지점 검토. **현재 구조를 읽은 설계 검토이며 삭제 코드 변경·DB 실행은 하지 않았다.**

## 결론

개인별 장부가 완전히 분리되어 있으면 자기 장부 삭제는 단순하다. 현재 돈독은 하나의 원장을 공유하며 한 거래가 여러 구성원의 자산에 영향을 줄 수 있다. 계정 ID를 따라 단순 cascade 삭제하면 다른 사람의 잔액·카드 이력이 손상되거나 DB 제약으로 실패한다.

‘탈퇴자 데이터 삭제’ 방향은 가능하지만, 개인별 소유 경계와 교차 거래 처리 규칙을 먼저 고정해야 한다. **작성자 기준으로 지우는 것과 경제활동 당사자 기준으로 지우는 것은 다르다.** 사용자 요청은 삭제 방향과 검토 요청이며 다른 구성원 데이터의 일괄 삭제나 임의 잔액 보정까지 승인한 것으로 해석하지 않는다.

## 실제 연결과 영향

| 상황 | 단순 삭제 결과 | 필요한 처리 |
|---|---|---|
| A가 B의 급여를 대신 입력 | 작성자=A 조건으로 삭제하면 B의 수입과 계좌 잔액이 사라짐 | B의 경제활동 기록과 A의 입력자 식별·작성 콘텐츠를 분리. 남길 자료의 개인정보·콘텐츠 삭제 적합성 검토 |
| A 계좌에서 B 계좌로 10만 원 이체 | 거래 전체 삭제 시 B의 실제 받은 10만 원도 잔액에서 빠짐 | 상대방의 잔액을 유지할 독립 기록 또는 기준 잔액 처리 필요. 상대방 정보·기존 메모를 그대로 복제하면 삭제를 우회하므로 금지 |
| A 카드대금을 B 계좌에서 20만 원 납부 | A 카드와 결제 전체 삭제 시 B의 장부 잔액이 20만 원 늘어남 | B의 실제 출금 효과와 A 카드 개인정보·연결을 분리. 돈이 실제 반환된 것처럼 환불을 생성하지 않음 |
| B 소유 카드 구매의 거래 당사자가 A | 당사자 기준 삭제가 B 카드 부채·명세·할부를 바꿈 | 카드 명의·구매 당사자·결제 계좌 각각의 유지/삭제 범위 확정 |
| A 계좌를 B 카드·체크카드·적금의 출금 계좌로 사용 | 남은 설정이 없는 계좌를 참조하거나 후속 저장/결제 실패 | 연결 해제와 새 계좌 선택 상태를 지원하고 동작을 안내 |
| 환불이 이미 B 계좌로 반환됨 | 원 구매만 삭제하면 환불·결제 배분이 고아가 되거나 합계 불일치 | 구매·회차·명세·결제·환불을 묶어 처리. 남은 사람의 실제 자금 효과 보존 여부 결정 |
| A가 가계부·공동 분류·B 자산을 처음 생성 | 생성자 FK를 cascade로 바꾸면 B의 가계부/분류/자산까지 삭제될 수 있음 | 공동 구조의 생성자 개인정보와 객체 생존을 분리. 소유자를 임의로 B로 바꾸지 않음 |
| A가 B 거래를 수정하며 메모에 A 개인정보 입력 | 작성자/당사자만으로 삭제 범위를 정하면 메모·audit에 A 정보가 남을 수 있음 | 자유문·변경 이력·로그를 포함한 삭제 범위와 권리행사 절차 필요 |

모든 금액 예시는 기준일 당일 이후의 유효 거래라는 전제다. 기준일 이전 거래는 이력 삭제와 현재 잔액 변화가 분리되므로 같은 보정식을 일괄 적용하면 이중 보정한다.

## 코드에서 확인한 근거

- `TransactionService.create`: 거래 당사자를 작성자와 별도로 검증하고, 이체 한 건에 출발 음수·도착 양수 posting을 함께 만든다. [구현](../../../backend/src/main/java/com/dondok/transaction/application/TransactionService.java)
- `CardPaymentItemService`: 카드 명의자를 당사자로 기록하면서 사용자가 고른 결제 계좌에서 출금한다. 명의자·작성자·출금 계좌가 서로 다를 수 있다. [구현](../../../backend/src/main/java/com/dondok/settlement/application/CardPaymentItemService.java)
- `asset_current_balance`: 기준일 잔액에 기준일 이후 유효 posting을 합산한다. 이력 삭제가 남은 사람의 잔액에 바로 영향을 준다. [V18](../../../backend/src/main/resources/db/migration/V18__treat_opening_balance_as_dated_anchor.sql)
- 가계부 생성자, 구성원, 자산 명의자·작성자, 분류 작성자, 거래 당사자·작성자·수정자가 FK로 연결되어 있다. 사용자 또는 member 한 행의 삭제로 해결되지 않는다. [V1](../../../backend/src/main/resources/db/migration/V1__initial_schema.sql), [명의자 NOT NULL V29](../../../backend/src/main/resources/db/migration/V29__require_individual_asset_owner.sql)
- 구매·환불·회차 배분·결제 배분에 원거래 참조가 남아 단순 삭제를 제한한다. [V11](../../../backend/src/main/resources/db/migration/V11__card_purchase_corrections_and_refunds.sql)
- 현재 탈퇴는 마지막 구성원이면 가계부를 삭제하지만 나머지가 있으면 공동 이력 보존 및 계정 필드 치환을 수행한다. [현재 탈퇴 코드](../../../backend/src/main/java/com/dondok/auth/application/AccountWithdrawalService.java)

## 권고하는 정책안 — 아직 미확정

1. 계정 개인정보·인증정보·세션·초대·프로필·연결 식별자는 삭제한다. 마지막 구성원은 가계부 전체도 삭제한다.
2. 탈퇴자에게만 귀속되는 자산·경제활동·작성 콘텐츠는 삭제한다. 다른 사람의 경제활동을 대신 입력했다는 이유만으로 그 사람의 금액 기록까지 지우지 않는다. 다만 탈퇴자가 만든 텍스트 등을 유지하는 근거로 이 구분을 쓰지 않는다.
3. 양쪽 사람과 연결되는 거래는 다른 구성원 자산의 **탈퇴 직전 현재 잔액 보존**을 우선하는 안을 검토한다. 개인정보 없는 기준 잔액 조정 또는 남은 사람에게 독립적으로 귀속되는 기록으로 분리할 수 있는지 검증한다. 어떤 형태도 자동으로 익명정보 또는 Apple 기준 충족이 되지는 않는다.
4. 잔액만 유지해도 과거 일별 잔액·이체/적금/투자 통계·환불 경로는 달라질 수 있다. ‘영향 없음’이라고 표시하지 않는다. 남는 개인 기록·상대 정보 제거·통계 변화의 구체적 예시를 다음 설계에서 비교한다.
5. 삭제의 영향은 서버 미리보기에서 본인 자산·거래, 다른 구성원 잔액 변화, 연결 해제, 카드 영향으로 보여준다. 검토한 snapshot이 바뀌면 412로 중단하며, 삭제 전체는 트랜잭션·동시성 방어로 처리한다. 다른 구성원의 승인을 필수 탈퇴 조건으로 만들지 않는다.

운영자 또는 전 구성원의 포괄 면책 동의로 손상된 잔액이나 개인정보 보존을 정당화하지 않는다. 삭제 확인문에는 복구 불가·공동 기록 영향·백업 잔존 기간을 실제 구현에 맞춰 알린다.

## 검증 범위

대리 입력, 교차 소유 이체·체크카드 지출·카드 결제, 분할 결제·부분 환불, 기준일 이전 거래, 명의 변경 이력, 탈퇴자가 생성한 가계부/분류, 다른 구성원의 동시 저장·탈퇴, 과거 soft-delete·audit·idempotency 자료, 백업 복구에서 개인정보 재등장 여부를 검증한다. 소스 읽기만으로 이 시나리오가 이미 통과했다고 주장하지 않는다.

Apple은 계정 삭제 시 다른 사람에게 공유한 사용자 작성 콘텐츠도 삭제할 것을 설명한다. 법적 보존 의무가 있다면 근거를 고지해야 하며 공동 이용자의 편의만으로 예외라고 단정하지 않는다. [공식 계정 삭제 안내](https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion)
